# 网站复用修改建议补充

日期：2026-11-16。

本文基于项目中现有 Markdown 文档整理，包括根目录 README、`docs/` 下的 P0/P1 文档、复用指南、计分器文档和《冷水坑杯3-项目需求文档-初版》全部 00–19 文档。

`docs/每赛季复用改造建议.md` 已经覆盖了赛季隔离、历史快照、正式整场结算、人工调整分、备份恢复、阶段控制、部署持久化和测试基线。下面列出与“每届明日方舟集成战略比赛都能复用此网站”直接相关、但当前建议中没有形成完整要求的补充项。

## 一、建议新增的最高优先级事项

### A. 赛事发布包与配置兼容性

当前文档分别讨论赛事名、赛道、规则、积分、品牌色、轮播和环境变量，但没有定义一份可验证的“本届赛事发布包”。每届比赛都需要把这些内容作为同一个版本发布，避免只改了赛道却忘记更新规则、只更新了文案却没有更新积分口径。

建议新增 `CompetitionProfile` 或等价的发布清单，至少记录以下内容：

- 赛事标识、赛事名称、届数、发布状态和发布时间
- 规则版本、赛道版本、位置模型、队伍人数和术语
- 原始成绩字段定义、倍率规则、取整方式、队伍倍率和晋级规则
- 报名、比赛、结果确认和归档阶段配置
- 轮播、Logo、背景图、帮助文案和联系方式
- 发布人、审核人、发布时间、代码版本和数据库 schema 版本
- 发布包内容哈希，便于确认运行中的配置和审核过的配置一致

发布流程应有草稿、校验、发布、冻结和回滚状态。发布前检查引用的赛道、规则、素材和计分字段是否完整。已经产生正式比赛后，影响历史解释的配置只能生成新版本，不能覆盖旧版本。

验收要求如下：

1. 新建一届比赛时可以导入或复制一份发布包。
2. 缺少规则、赛道、计分字段或素材引用时，发布前给出具体错误。
3. 发布后的配置可以导出为 JSON 或 Markdown 清单。
4. 历史页面显示该届发布包版本和校验值。
5. 同一发布包在隔离环境恢复后得到相同的规则和展示结果。

### B. 跨赛事数据导入与预览

现有 P1-1 解决了配置继承，但每次换一场新的集成战略比赛时，用户、队伍、成员、赛道选择和历史成绩仍可能需要人工重录。复用场景需要一条受控的数据导入路径。

建议补充以下导入范围：

- 用户名单和昵称
- 队伍、队长、队员和位置
- 赛道选择、分队、干员和参赛声明
- 已排比赛和比赛时间
- 已确认成绩、难度、倍率和证据文件引用
- 经过人工确认的历史上下文和人工调整分

导入流程应分为上传、解析、预览、校验、确认和提交。提交前展示新增、更新、冲突、无法匹配和将被忽略的记录。用户匹配应优先使用稳定账号标识，昵称只能作为人工辅助匹配字段。

导入必须支持 dry-run。校验失败时不写入任何业务数据。正式提交前生成导入批次号和备份，提交后可以按批次查看影响范围。导入后的分数不能绕过 P0/P1 的规则快照、结算状态和审计要求。

### C. 比赛申诉、重赛和最终冻结

初版比赛文档提到争议处理和比赛重赛，但当前复用建议主要关注管理员修改结果和审核标记，没有形成完整的申诉生命周期。不同届比赛如果没有统一的申诉期限和冻结规则，管理员容易在公布结果后继续修改排名。

建议定义以下状态：

```text
待提交 → 待确认 → 已结算 → 申诉中 → 申诉裁决 → 结果冻结
```

需要明确：

- 谁可以发起申诉，申诉截止时间如何配置
- 申诉必须提交哪些证据和说明
- 管理员、超级管理员和裁判是否拥有不同权限
- 申诉期间排名是否显示为暂定
- 裁决后是否允许重赛，重赛如何关联原比赛
- 结果冻结后只有哪种专项入口可以更正
- 更正后如何重新发布排名、导出文件和公告

重赛不能删除原比赛。原比赛应保留为被替换记录，新比赛关联原比赛并记录原因、操作者和最终采用的结果。

## 二、建议补充的安全和数据治理要求

### D. 账号、隐私和公开展示策略

现有文档确认账号跨届保留，昵称和头像继续跟随账号，但没有规定个人数据的展示、导出、删除和匿名化规则。公开队伍页、历史归档、API 和 Excel 导出都可能暴露个人信息。

建议补充：

- 公开页面只显示赛事所需的昵称、队伍和成绩字段
- 用户名、邮箱、登录信息和管理员备注不得进入公开 API 或公开导出
- 昵称变更是否追溯影响历史页面，需要作为可配置的展示策略
- 用户头像和队伍照片的公开访问范围、删除规则和失效处理
- 用户申请删除账号后的历史成绩如何匿名化并保留赛事证据
- 管理员导出文件的访问权限、有效期和下载审计
- 个人数据导出请求和人工处理记录
- 数据保留期限，尤其是截图、日志、导入文件和备份中的个人资料

这些规则应与“昵称和头像跟随账号”的 D14 决策一起写入复用指南，避免运营方在不同届赛事中采用不同口径。

### E. 生产安全基线

现有建议包含默认密钥和默认口令告警，但复用到多届比赛时还需要一份最小生产安全基线：

- 管理员密码重置和会话全部失效
- 超级管理员的可选多因素认证
- 登录失败次数限制和管理员接口速率限制
- 上传文件的大小、扩展名、实际 MIME 类型和文件名规范校验
- 图片和视频的解码限制，避免恶意文件占用资源
- CSRF、Cookie 安全属性、反向代理 HTTPS 配置和安全响应头
- 依赖漏洞扫描、镜像扫描和基础镜像更新周期
- SECRET_KEY、数据库密码和备份凭证的轮换方式
- 生产环境禁止调试模式和敏感错误堆栈

每届比赛复制实例时，应有一份不包含真实密钥的环境变量模板，并说明哪些值必须重新生成。

### F. 附件和素材生命周期

现有文档要求备份素材并检查引用完整性，但没有规定上传文件的长期管理方式。建议补充：

- 上传文件使用随机存储名，数据库保存原始文件名和 MIME 类型
- 限制单文件大小、单用户总量和单届赛事总量
- 计算内容哈希，避免重复保存相同文件
- 检测数据库引用丢失和目录中的孤儿文件
- 规定截图、队伍照片、轮播图和比赛视频的保留期限
- 删除文件前检查是否被历史比赛、备份或审计引用
- 迁移素材目录时保留路径映射和校验值
- 对外提供素材时使用安全路径或短期签名地址

## 三、建议补充的运维和交付要求

### G. 可观测性和故障告警

当前文档有 SystemLog、备份清单和测试报告，但缺少运行中的健康检查和告警要求。建议增加：

- `/health` 检查应用进程、数据库连接、schema 版本和素材目录
- `/ready` 检查服务是否完成 prepare、迁移和必要配置
- 结构化日志中的请求 ID、操作者、赛季、对象 ID、耗时和结果
- 换季、迁移、恢复、导入、积分重算和审计失败的告警
- 备份最近成功时间、备份完整性和剩余磁盘空间
- 当前活跃赛季数量、未结算比赛数量和待处理申诉数量
- 错误日志脱敏，不能记录口令、密钥和完整个人资料

健康检查应区分进程存活和业务可用。数据库未准备完成时，服务应明确返回未就绪状态。

### H. 恢复目标和灾难演练

P1-3 已提出备份和恢复演练，但还没有定义运营目标。每个部署实例应明确：

- 可接受的数据丢失窗口，也就是 RPO
- 恢复到可读页面和可写业务的目标时间，也就是 RTO
- 谁负责发起恢复、谁负责确认恢复结果
- 恢复期间是否进入只读模式
- 恢复后如何重新生成或轮换密钥
- 恢复后如何验证数据库、素材、附件引用和规则快照
- 恢复演练结果保存在哪里，多久重复一次

恢复演练应覆盖空库、已有赛季、已归档赛季、未结算比赛、人工调整分和带附件的比赛，而不是只验证数据库能打开。

### I. CI、发布和兼容性矩阵

项目文档提到测试和 CI，但没有形成每届复用发布的固定检查矩阵。建议把以下检查设为发布门槛：

- Python 版本和依赖锁定
- SQLite 与 MySQL 的迁移和恢复
- 空库初始化、旧库升级和重复 prepare
- 当前赛季、归档赛季和无活跃赛季
- 正常成绩、0 分、弃权、分段比赛和人工调整
- 管理员、超级管理员、队长和选手的关键路径
- 桌面和移动浏览器的页面冒烟
- 规则、赛道、术语、轮播和导出文件的配置替换
- 备份、恢复、导入和审计失败回滚
- 文档中的路由、环境变量和命令与实际代码一致

每次发布生成一份机器可读的测试报告，绑定代码提交、schema 版本、发布包版本和镜像版本。

## 四、建议补充的产品和接口要求

### J. 赛程公平性和异常场景

初版文档已经指出时间偏好没有接入匹配算法，但复用建议还没有为赛程公平性定义验收标准。建议补充：

- 时间偏好重叠度如何计算
- 选手没有可用时间时如何处理
- 同一队员连续比赛、休息间隔和跨日比赛的限制
- 手动调整赛程时如何保留原因和操作者
- 轮空、迟到、未到场、网络故障和临时换人的处理
- 同一对手重复匹配的限制
- 赛程冲突的检测和管理员覆盖规则

这些规则应与正式比赛、日程分段和弃权结算分开定义，避免把日程段当成额外比赛。

### K. 统一 API 契约和外部集成边界

初版 API 文档已经提出 `/api/v1/`、统一响应和 OpenAPI，但复用建议没有把它纳入每届上线要求。建议补充：

- 公开读取 API 与管理员写入 API 分开
- API 返回当前赛季、归档赛季和数据状态
- 分页、排序、过滤、字段选择和最大返回量
- 错误码、请求 ID 和幂等键
- API 认证、权限范围和密钥轮换
- 旧版本 API 的兼容期限
- 导出任务异步化和大数据量下载方式
- 外部计分器或报名系统的导入协议

如果未来集成离线计分器，应定义服务端唯一计分规则、规则版本、客户端明细格式和重复提交策略。浏览器本地计算结果只能作为输入证据，不能直接成为最终积分。

### L. 公开结果快照和发布记录

排行榜页面可以实时变化，但赛事对外公布的冠军、晋级名单和最终积分需要一个可复核的发布快照。建议补充：

- 结果发布批次、发布时间和发布人
- 发布时采用的规则、赛季、积分和调整分版本
- 参赛队伍、排名、晋级名单和比赛统计的快照
- 公开结果文件的哈希
- 发布后更正时保留旧版本和更正说明
- 公开页面显示“暂定”“已发布”或“已更正”状态

这可以避免同一个历史页面因为后台后来纠正数据而无法解释当时对外公布的结果。

### M. 可访问性和移动端验收

初版 UI 文档已经指出 ARIA、键盘导航和 Toast 等不足，但复用建议没有将其纳入每届验收。建议补充：

- 关键表单可用键盘完成
- 状态颜色同时有文字或图标表达
- 图片具有替代文本
- 错误信息关联到具体输入框
- 移动端完成注册、入队、约赛、提交成绩和查看结果
- 小屏幕下表格、弹窗和长名称可用
- 支持主流 Chrome、Edge、Safari 和 Firefox 的当前稳定版本

## 五、建议补充的文档治理要求

### N. 建立单一需求矩阵

当前文档存在历史需求、P0/P1 实施记录、复用指南、计分器 README 和初版设计之间的时间差。例如初版通知文档仍描述通知功能，现行建议已决定删除通知功能。建议新增一份需求矩阵，包含：

| 项目 | 当前结论 | 权威文档 | 实现状态 | 验收入口 | 备注 |
|---|---|---|---|---|---|
| 通知功能 | 删除或恢复 | 复用建议 | 未实现/已删除 | 对应测试 | 初版文档标为历史资料 |
| 计分器集成 | 进行中 | [复用建议第 8、9 章](./每赛季复用改造建议.md#8-p4-计分器集成) | 超管发布、换届配置和选手计分预览已接通 | 规则发布、计算对拍、提交与结算联验 | 正式提交目前使用手填成绩 |
| 赛事规则 | 按届冻结 | P0-6 与发布包 | 已实现/待补发布流程 | 历史页面 | 需要版本号 |

历史初版文档应标注“设计参考”或“已废弃”，避免运营人员将旧路由、旧审批流和旧通知规则当作当前系统行为。

### O. 每届运营交接包

每届比赛结束后应生成一份交接包，包含：

- 赛事发布包和配置清单
- 赛季、schema、代码和镜像版本
- 管理员和裁判操作说明
- 当前备份和恢复演练记录
- 未结算、申诉、人工调整和历史核对清单
- 最终结果发布文件和导出文件
- 已知问题、临时配置和下一届待办

交接包使下一届运营可以从已验证状态开始，而不依赖开发者记忆或聊天记录。

## 六、建议的补充实施顺序

1. 赛事发布包、文档权威矩阵和交接包
2. 数据导入预览与批次回滚
3. 申诉、重赛和结果冻结
4. 隐私、安全和附件生命周期
5. 健康检查、日志告警、RPO/RTO 和恢复演练
6. API 契约、公开结果快照、可访问性和移动端验收

这些事项可以与现有 P1-3、P1-4、P2 和 P3 交叉安排。每一项都应在发布清单中写明实施状态、验证命令和负责角色。
