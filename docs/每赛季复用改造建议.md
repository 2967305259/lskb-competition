## 1. 结论摘要

1. **「换赛事」已经做到改配置不改代码**，赛事名、术语、队制、赛制默认值、品牌色、赛季模型、往届归档均已参数化；剩下的问题不是「换名」，而是**换季时的一致性**。
2. **换季会误伤往届数据**：积分重算全表清零、遍历所有已完成比赛，且用**当前**赛道难度参数换算（`scoring.py:70-133`）。换届后调整难度或点「重置积分」，历史积分会被按新规则改写。
3. **换季的原子性依赖唯一一次提交**：`new_season()` 在末尾提交一次（`app.py:3272`），但 `Setting.get_instance()` 自身会 `commit()`（`app.py:670-677`），首次建 `Setting` 时会提前提交一次；加上没有预检与幂等，重复点按仍可能产生多个新赛季。报名/比赛时间、晋级数等配置也不继承，每届必须人工重填。
4. **数据库迁移只在 SQLite 生效且异常静默**：`_migrate_schema()` 直连 `.db` 文件（`app.py:4271-4277`），补列清单不含赛季相关列，`except` 仅打印（`4309-4310`）；`gunicorn --workers 4`（`docker-entrypoint.sh:27-33`）下四个进程会并发执行迁移。
5. **赛季隔离已收敛但有漏点**：选手胜负统计跨届累计（`app.py:1866-1868`、`1935-1937`）、`JoinRequest` 无赛季维度（`1709-1711`）、按 id 直取的详情页无赛季校验（`1164`、`2360`、`2611`）。
6. **P4/P5 计分器集成已验收**。超级管理员按届启用，正式提交由后端重算，整场历史保留绑定规则。见第 8、9 章。

## 3. P0 往届数据安全

> 本节为本次改造重点，逐条给出「现状证据 → 触发场景 → 改法 → 验收」。

### 3.1 P0-1 积分重算按赛季隔离

**现状证据**

| 位置 | 当前行为 |
|---|---|
| `scoring.py:86-94` | `TeamMember.query.all()` / `Team.query.all()` **全表清零** |
| `scoring.py:96-99` | 遍历**所有** `finished` / `forfeit_a` / `forfeit_b` 比赛 |
| `scoring.py:107-118` | 按 `roguelike` key 取**当前**赛道配置换算倍率 |
| `scoring.py:133` | 函数内部自行 `commit()`，把事务边界写在库函数里 |
| `app.py:3183` | `POST /admin/reset-scores` 直接调用 |
| `app.py:3493` | 管理员改分后调用（`3486` 注释：通知必须先建，因为重算内部会 commit） |
| `app.py:4102` | 弃权流程调用 |
| `app.py:688` | `Match.tournament_id` 已存在，可直接用于过滤，无需加列 |
| `app.py:447-448` | `Tournament.teams` / `Tournament.matches` 关系已存在 |

**触发场景**

- 换届后调整赛道难度 → 点「重置积分」→ **往届所有队伍与队员积分按新参数重写**，`/history` 榜单跟着变。
- 管理员修改一场旧赛季比赛的结果 → 触发全库重算，旧赛季积分同样漂移，且耗时随累计比赛数线性增长。

**改法**

1. 签名改为 `recalculate_all_scores(tournament_id=None)`：`None` 时取唯一活跃赛季；无活跃赛季则无副作用返回，多活跃赛季则报错拒绝。指定往届 ID 只能由超级管理员专项纠错流程调用（D10 已确认），普通重置入口不能借参数越权。
2. 清零范围按赛季收窄：`Team.query.filter_by(tournament_id=tid)`；队员用 `TeamMember.join(Team).filter(Team.tournament_id == tid)`。
3. 比赛范围加 `Match.tournament_id == tid`，并按 P1-5 只收取已确认结算的整场成绩，排除独立日程段；弃权胜负已定但尚待补交/结算的比赛不能只因 `forfeit_a/b` 就进入积分。`_update_team_scores(match)` 按正式对阵所属赛季调用重算，不从分段重复累计。
4. 移除 `scoring.py:133` 的内部 `commit()`，由调用方（`reset_scores` / `edit_match_result` / 弃权流程）统一提交；同时删掉 `app.py:3486` 那条「必须先建通知」的隐式约束注释。
5. **历史数据兼容**：`matches.tournament_id IS NULL` 的比赛不会被任何赛季命中。**已定采用「人工确认清单」**：脚本按「`team_a.tournament_id` → `team_b.tournament_id` → `created_at` 落在赛季区间」推算出建议值，只输出报告（比赛 id、双方、建议赛季、推断依据），**不直接写库**；人工核对后再执行写入，脚本可重复执行。当前数据核查：主库 0 场比赛，备份库 3 场且全部带 `tournament_id`，暂无需要回填的行。
6. 后台普通「重置积分」明确仅当前赛季；按 D10，指定往届重算仅在超管专项纠错入口提供作用域与影响提示，不能在普通入口直接切换到往届。

**验收**

- 造两届数据：切到新赛季、改难度、点重置 → `/history/<旧届>` 的队伍榜与队员榜数值不变。
- 普通入口修改旧赛季比赛 → 后端拒绝且库内值不变；超管从专项纠错入口修改后只有该届积分变化，新赛季不受影响，并保留前后值与原因。
- 空库（无 `Tournament`）调用 `recalculate_all_scores()` → 正常返回，不抛异常。
- 重算后 `SystemLog` 记录本次作用域（届数 + 队伍数 + 场次数）。

**工作量 / 风险**：小 / 中。风险集中在历史 `tournament_id` 为空的回填，回填规则必须先与运营确认。

### 3.2 P0-2 倍率快照

**现状证据**

| 位置 | 当前行为 |
|---|---|
| `app.py:471-473` | `Roguelike.difficulty_min` / `difficulty_max` / `difficulty_step` 全局共享、可按赛季修改 |
| `app.py:476-478` | `get_multiplier()` 每次实时读取当前参数 |
| `app.py:695-696` | `Match` 只存 `player_a_difficulty` / `player_b_difficulty`，**不存倍率、不存最终分** |
| `scoring.py:110-118` | 重算时用当前 `Roguelike` 重新换算 |
| `scoring.py:125-131` | 队伍分 = 队员分之和 × 该赛季 `bonus`（`bonus` 已按赛季隔离） |

**触发场景**

- 难度阶级从 `0.1` 调到 `0.2` → 所有历史场次的倍率被重新解释，历史积分改变且无法复现原值。
- 赛道被删除后 `rl` 为 `None` → 倍率退化为 `1.0`（`scoring.py:112`），历史成绩静默变低。
- 争议复盘时无法说明「当时按什么倍率算的」。

**改法**

1. 正式对阵的成绩记录（现有 `Match` 的整场归属记录）增 `player_a_multiplier`、`player_b_multiplier`，类型用 `db.Numeric(8, 4)`；同时关联或保存当时的难度区间、步长、换算/取整口径及其版本。仅存倍率不足以支持以后纠正难度，独立日程段不另设一份可结算成绩。
2. 写入时机：新比赛首次计分时固化规则与双方倍率；在允许修改全局难度规则前，检查并完成已有成绩的快照，不能等下次重算才取已改变的参数。改规则、补快照和审计必须有明确事务边界。
3. 修改**原始成绩**时保留原倍率与规则；修改**难度**时按该比赛已固化的历史规则重新计算倍率并记录前后值，不能清空快照后读取当前全局规则。新赛季新比赛使用新的参数。
4. 可选冗余列 `player_a_final_score` / `player_b_final_score`（`int(raw * multiplier)`），用于排行榜与明细对账；与 `scoring.py:29-31` 的截断口径保持一致。
5. 旧数据无快照时先输出核对报告，由人工确认采用的历史参数或迁移基准后再回填（D6）；缺失的旧规则不能声称已自动恢复。未完成核对前禁止用当前参数静默重写已有历史成绩。

**验收**

- 记录某历史场次当前积分 → 把 `difficulty_step` 从 `0.1` 改为 `0.2` → 重置积分 → 该场次及所属队员总分不变。
- 新赛季新比赛按新参数计算，快照值与 `Numeric` 精度一致（如 `1.2000`）。
- 旧数据按确认的基准回填一次，二次执行无变化；缺少依据的记录列入报告，不能静默换用当前规则。
- 只改原始成绩时倍率不变；获准纠正历史难度时使用当时规则，改全局参数不影响纠错结果。
- 后台比赛详情能看到该场的倍率与最终分，便于复核。

**工作量 / 风险**：中 / 中。倍率、规则版本和旧数据核对需一起完成；取整口径（先乘后截断）必须与确认的 `calculate_final_score()` 规则一致，否则排行会出现 ±1 差异。

### 3.3 P0-3 迁移正规化与启动期并发

**现状证据**

| 位置 | 当前行为 |
|---|---|
| `app.py:4271-4277` | 直连 `DB_FILE`（`sqlite3.connect`），**MySQL 部署完全不执行** |
| `app.py:4281-4294` | 补列清单仅 12 项，缺 `teams.tournament_id`、`matches.tournament_id`、`tournaments`、`carousel_items`、`rules` |
| `app.py:4217-4268` | `_migrate_teams_unique()` 建新表重建 `teams`；`4262-4263` 的 `SELECT` 依赖 `tournament_id` 列已存在 |
| `app.py:4309-4310` | `except Exception` 仅 `print` 后关闭连接，**迁移失败不阻断启动** |
| `app.py:4400-4403` | `create_all()` + `_migrate_schema()` 在模块级 `create_app()` 内执行 |
| `docker-entrypoint.sh:27-33` | `gunicorn --workers 4 app:app` → 4 个进程**并发**执行建表/迁移 |
| `app.py:129`、`4329` | `Migrate` 已初始化，但仓库无 `migrations/`，从未 `flask db init` |
| `docker-compose.yml` | 默认 MySQL，与「迁移只支持 SQLite」直接冲突 |

**触发场景**

- MySQL 部署：老库升级后新列不存在 → 查询/写入直接报错，且启动日志无任何提示。
- 4 个 worker 同时重建 `teams` → `table teams_new already exists`、数据被并发覆盖。
- 迁移中途失败被吞 → 结构停留半成品，问题延后到业务请求才暴露。

**改法（两级，本批只做最小闭环）**

1. 用 `sqlalchemy.inspect(db.engine)` 检查实际目标库，采用显式、版本化迁移；模型用于校验差异，不能只凭「缺什么列就补什么」替代数据回填、索引、外键与联合唯一约束迁移。SQLite / MySQL 复用迁移意图，DDL 差异分别处理。
2. 新增 `schema_version(version, applied_at)` 表，迁移按版本号幂等推进；已存在的列跳过。
3. 失败即 `raise` 并终止进程（fail-fast），日志输出表名、列名、原始异常；不允许「打印警告后继续」。
4. 单进程执行：`docker-entrypoint.sh` 在 `exec gunicorn` 之前先跑一次迁移命令（`flask db upgrade` 或独立脚本），成功后再启动多 worker；纯 SQLite 本地开发可用文件锁或 `BEGIN IMMEDIATE` 兜底。
5. 迁移前完成一致备份：运行中的 SQLite 使用 backup API，或真正停写、处理 WAL/checkpoint 后复制；不能直接 `shutil.copy2` 活跃数据库文件。MySQL 使用一致性 dump，并验证实际文件、退出码与清单；只显示命令不算备份成功。备份失败中止迁移，按批次保留最近 5 份（详见 P1-3）。
6. 顺序保证：`_migrate_teams_unique()` 依赖 `tournaments` 表已存在（`app.py:4230-4234`），必须排在 `create_all()` 之后；MySQL 无 `PRAGMA foreign_keys`，需分支处理。

**为什么不用已初始化的 Flask-Migrate（留好切换点）**

`Migrate` 已经在 `app.py:129`、`4329` 完成初始化，但仓库没有 `migrations/` 目录，从未 `flask db init`，等于**没有迁移基线**。本批仍然自研 `schema_version`，取舍如下：

| 维度 | 直接接 alembic | 本批自研 `schema_version` |
|---|---|---|
| 起点 | 无 `migrations/`，需先建基线 | 无历史包袱 |
| 老库 | 模型与线上结构本身不一致（缺列），自动生成的 diff 不可信；`stamp` 到哪个版本要先摸清实际结构 | 先识别已支持的旧库结构，再按显式版本迁移并校验数据/约束，不对未知结构盲补 |
| 运维 | 需在部署流程显式执行 `flask db upgrade`，多 worker 下还要保证只跑一次 | 同样在服务启动前单进程迁移，不在每个 worker 内自愈 |
| 能力 | 支持 downgrade、分支、revision 历史 | 本轮只实现已验证的向前迁移；复杂回退依赖匹配版本的整套备份 |
| 适用 | 结构频繁演进、多人协作 | 单实例、表数量有限、一次性补列 |

结论：**当前阶段沿用最小版本化迁移方案，但不封死后续路径**。未来切换 Alembic 前，须验证所有已支持库已迁移到一致基线，再建立并核对 revision；`stamp` 只标记版本，不会实际修复 schema，不能把「stamp head」当成自动升级或直接删除原迁移的依据。

**验收**

- 用旧库副本启动：缺失列被补齐，`schema_version` 有记录，`teams` 唯一约束为 `(tournament_id, team_name)`。
- 故意制造迁移失败 → 进程退出码非 0，日志可直接定位到表/列，容器不会带病提供服务。
- MySQL 环境启动后 `SHOW COLUMNS FROM matches` 含 `tournament_id`。
- 4 worker 并发启动 → 无 `already exists` 类错误，无重复建表。

**工作量 / 风险**：中 / 高。改动的是启动路径，必须在数据库副本上完整演练一遍再上线；建议保留旧版镜像以便回滚。

### 3.4 P0-4 换季事务化、前置校验与备份

**现状证据**

| 位置 | 当前行为 |
|---|---|
| `app.py:3241-3243` | 取 `Setting` 与 `Tournament.get_active()`，届数直接 +1 |
| `app.py:3247-3250` | 旧赛季置 `is_active=False`、状态改 `finished` |
| `app.py:3252-3259` | 删除旧赛季队伍的 `pending` 邀请与加入申请 |
| `app.py:3260-3264` | 新建赛季，**只继承 `bonus_score`** |
| `app.py:3266-3267` | 批量把非管理员的 `User.status` 归零（**全表写**，不区分是否本届参与者） |
| `app.py:3268` | `TimePreference.query.delete()` 清空全部时间意愿 |
| `app.py:3269-3271` | 改 `Setting.tournament_name`、`advance_count=0`、`registration_open=True` |
| `app.py:3272-3273` | 唯一一次 `commit()`，随后才写 `SystemLog` |
| `app.py:452-454` | `get_active()` 用 `.first()`，无排序、无唯一性保护 |

**事务边界澄清**：只有业务链路内不存在提前提交，且业务、审计与幂等结果统一提交时，才能保证完整原子性。`Setting.get_instance()` 等辅助函数内部提交，以及提交后再写日志，都会破坏这一前提；不能仅凭 `new_season()` 末尾出现一次 `commit()` 判为已完成。

**触发场景**

- 页面卡顿或手滑连点两次「开启新赛季」→ 产生两个新赛季，榜单随机命中其中一个。
- 上届还有未完成的比赛就换季 → 那些比赛永久停留在旧赛季且无法收尾。
- 换季成功但日志写入失败 → 事后无法追溯谁在何时换的届。
- 库里存在多条 `is_active=True`（历史遗留）→ `get_active()` 返回哪条不确定，全站数据跟着漂。

**改法**

1. **预检**（提交前）：
   - `Tournament.query.filter_by(is_active=True).count() != 1` → 拒绝并提示先修复。
   - 未完成比赛：按正式对阵列出尚未确认结算的待收尾场次，包括弃权胜负已定但仍待补交/结算的对阵；不能把每个日程段的 pending 当成一场独立未完赛。**D16 已确认保留强制换季**：普通切换先提示并要求显式选择强制；强制时展示未完成清单、必填原因，随换季审计保存，并冻结这些场次的普通提交。不得擅自将未完赛标为已完成、清零或自动取消；以后如需纠错，只能按 D10 走专项流程。
   - 同名或同届已存在 → 拒绝。
2. **幂等与并发**：服务端签发请求令牌，提交携带 `idempotency_key` 和 `expected_current_season_id`；持久化令牌与处理结果，同一令牌再次请求返回同一结果。事务内用锁或条件更新重新校验当前赛季及预检条件，防止不同令牌并发切换；基于旧页面的请求不得再创建下一届。届数唯一约束是额外防线，**不能代替请求幂等**（顺序重复请求可以生成不同届数）。
   - 请求重放先查已提交的幂等结果，再决定是否执行预检/备份，避免成功换季后的旧请求被当作新一届操作。处理中的并发请求等待或返回明确处理中状态，不能各自切换。
3. **备份前置**：调用 P0-3 的备份函数；备份失败则中止，不做任何写入。
4. **事务与日志**：新旧赛季状态、配置继承、重置项、`SystemLog` 与幂等结果在同一事务提交；`try / except: rollback + raise`。移除 `Setting.get_instance()`、重算和日志辅助函数的隐式提交。审计写入失败必须回滚业务，不能把「以后重试日志」算作原子性已通过。
5. **重置项显式化**：把「必然重置」的字段写成常量列表（`advance_count=0`、`registration_open=True`、`TimePreference` 清空、非管理员 `status=0`），并在页面提示；`team_size` / `allow_incomplete_teams` 当前是「保留上届值」，先保持现状并注明，是否改为可勾选继承放到 P1-1。
6. **审核流程：已定删除**（D1=②）：`approval_status`（`app.py:493`）从不参与准入判断——`is_approved()`（`app.py:536-537`）全仓 **0 处调用**，登录、建队、报名都不校验；后台「审核通过/拒绝」（`app.py:3345-3374`）只改字段并写一条无人查看的通知。因此当前并不存在「上届被拒用户本届被拒」，他们照常参赛。处理方式：
   - 删除 `approval_status` 字段（需迁移）、`/admin/approvals`（`3331-3342`）、`approve_user` / `reject_user`（`3345-3374`）、`admin/approvals.html`、`is_approved()`；
   - 注册后直接可用，报名改为直接生效；
   - 换季不再需要讨论 `approval_status` 口径，`User.status` 归零即可；
   - 复用指南里「注册 → 待审核 → 通过」的流程描述同步删除。
7. **批量更新前统计**：`User.status` 归零前先 `count()` 受影响行数并写入日志，便于事后核对。
8. 活跃赛季读取检查基数：多条 active 必须显式报错并提供修复报告，不能排序后随便取一条；空库允许初始化，但重算不能回退到全库。换季提交时必须确认恰有一个旧活跃赛季，并通过事务锁或条件更新保证最多一个新活跃赛季。

**验收**

- 相同令牌连续或并发 POST 两次 → 只产生一个赛季、返回相同结果；不同令牌但携带同一旧赛季 ID 时最多一次成功。
- 备份失败、事务中失败或审计写入失败 → 均未切换、无新赛季与幂等成功结果残留；多 active 被拒；无 active 重算不触碰孤儿积分。
- 存在未完成比赛时给出清单；未显式选择强制则拒绝切换，强制时校验权限与必填原因，记录清单并冻结普通提交；旧有成绩保留，不自动改为完成或取消。
- 人为制造提交失败（临时唯一约束冲突）→ 旧赛季仍 `is_active=True`、无新赛季残留、pending 邀请与申请未被删除。
- 换季后 `SystemLog` 恰好一条 `new_season`，内容含新旧届数与影响用户数。
- `/history` 届数、榜单与首页统计在新旧赛季之间切换正确。

**工作量 / 风险**：中 / 中。强制换季须与归档只读及超管专项纠错一致；幂等、清单冻结和备份不能仅靠前端防连点或提示实现。

### 3.6 P0-5 归档后端写保护与专项纠错

**现状证据（2026-11-07 基线）**

- `app.py:2566` 的队伍删除入口会删除关联比赛，未统一校验归档赛季。仅在详情页隐藏按钮无法阻止直接构造 POST。
- `app.py:2505` 的用户删除入口保护了比赛/`ScoreLog` 引用，但无比赛的往届队伍、成员关系仍需保护；不能把「没有成绩」等同于「没有历史价值」。
- 改队员积分、改成员、排赛/拆分/确认、弃权、成绩提交等写入口未形成统一的赛季与阶段检查，前端只读不能代替后端授权。
- `ScoreLog.old_result/new_result` 当前是 `String(20)`（`app.py:732-733`），而改结果入口已经拼接成绩、难度和胜负等长文本；在 MySQL 上可能失败或截断，不能据“已建日志模型”认定前后值审计完整。

**改法**

1. 明确状态：`is_active` 表示当前运营赛季，`status` 表示报名/比赛/结束阶段；当前赛季结束不等于已经切换归档。不能仅靠 `status == 'finished'` 或页面 URL 判断是否可写。
2. 建立统一写入守卫，按「动作、目标归属赛季、阶段、操作者权限」检查。先查目标对象及其关联归属，再执行业务；URL、表单中手填的 `tournament_id` 不能覆盖真实归属。比赛、队伍、成员跨赛季关联应拒绝；孤儿数据隔离待核对。
3. 所有普通入口拒绝写往届：队伍/成员的改删、原始成绩/难度/总分修改、排赛/拆分/确认/驳回、邀请与申请处理、赛道与位置选择、弃权和截图/成绩提交。覆盖 GET 以外的全部写请求，错误返回不产生提交或文件副作用。
4. **D10 已确认：超级管理员可专项纠错**。仅通过独立入口执行，必填原因，展示影响范围，按该届规则重算，业务与审计同事务提交。审计含操作者、时间、赛季、目标 ID、前后值、原因及影响榜单；普通改分页面仍只读，普通管理员不得获得该例外。
   - 审计字段采用能完整容纳结构化前后值的类型，并纳入版本迁移；不得因旧字段长度不足截断证据。SQLite 与 MySQL 都要验证实际持久化值及事务失败行为。
5. 删除前核查历史依赖，阻断会级联破坏归档的队伍、用户、成员、赛道等删除；账号/赛道停用与历史记录保留分开处理。`ScoreLog` 永不删除（D8），其关联不能因删用户/队伍而被级联抹除。手动素材清理仍按 P3-6 明示的范围执行。

**验收**

- 以选手、队长、管理员身份直接向往届对象 ID 发起各类改删请求：全部被拒，积分、关系、审计凭证与素材无非预期变化。
- 当前赛季合法操作仍通过；归属冲突、孤儿对象、多 active 状态不能借默认值放行。
- 删除拥有往届成员关系但没有比赛的用户/队伍也不会破坏历史；有 `ScoreLog` 引用的对象不可级联删除。
- 验证超管专项纠错的权限、必填原因、历史规则、前后值、审计失败回滚及新季不受影响；普通管理员、选手、队长不能借该入口越权。

### 4.6 P1-6 人工改分持久化与审计

**现状证据（2026-11-07 基线）**：`app.py:2586` 直接写 `TeamMember.final_score`，汇总可能读取当前活跃季 bonus；`app.py:2618` 另一入口直接覆盖总分并称为最高优先级，但全量重算会重新覆盖。当前无法可靠区分「原始比赛累计」与「人工调整」。

**D11 已确认：独立调整分，重算保留，可审计撤销**

保留人工修正能力，改为独立的调整分记录，绑定赛季、队伍/成员、操作人、时间、原因、调整值及撤销关系；比赛累计与调整分分别存储/展示。重算只重建比赛累计，再按确认后的公式叠加有效调整；撤销用反向/撤销记录，不删除审计。取消的是“直接覆盖可重算累计字段”的实现，不取消人工调整能力。队伍汇总使用该成员所属赛季 bonus。

**队伍加成倍率的源码含义**：`Tournament.bonus_score` 是赛季统一系数，后台“积分配置”的“加成倍率”（`app/templates/admin/score_config.html:31-33`）写入该届字段（`app.py:3117`）；模型/默认配置为 500，运行时取所属赛季保存值。它作用于已经完成难度换算的队员累计之和，与单场胜负无关；当前同一赛季所有队伍使用相同正倍率时，只放大分值、不改变排名。这是现有实现说明，不是新增单挑加分规则。

**D11 倍率顺序已确认**：先将有效人工调整计入队员积分，再参与队伍加成倍率。公式为 `队员总积分 = 已确认结算的整场比赛积分之和 + 有效人工调整分之和`，`队伍积分 = 所属成员总积分之和 × 所属赛季 bonus`。例如全队调整前累计 1000、某队员调整 +10、bonus=500，队伍分为 `(1000+10)×500=505000`；不采用 `1000×500+10`。

**实施要求**

1. 同一时刻不得存在两种总分来源互相覆盖。总分的可重建公式必须明确，重算、详情、排名与导出一致。
2. 已有人工改分先输出对账报告，比较存储总分与可重建比赛分；差额不一定全是人工调整，可能来自旧倍率、缺数据或旧 bug，不能自动把差额全部造为调整记录。
3. 确认后迁移并保存依据、前后值与审计，不删除原始成绩记录；旧赛季操作禁止误用当前 active 的 bonus。
4. 按已定顺序在难度换算后的队员累计上叠加调整，再乘队伍 bonus；保留比赛分现有确认的取整口径。调整分是队员积分单位，不再额外乘一次难度倍率，撤销时也按相同公式重建。

**验收**：人工调整后反复重算数值不丢失，撤销可追溯且不会重复叠加；比赛累计与调整明细可对账。验证 `(1000+10)×500=505000`，撤销后恢复 `1000×500=500000`；另验证两届不同 bonus、归档写保护及审计失败回滚，不保留直接覆盖累计字段的旁路。

**依赖 / 风险**：账本与倍率顺序均按已定 D11；依赖 P1-5 的整场结算、P0-1 的事务边界和 P0-5 的权限。未知历史差额须人工核对。

### 5.4 P2-4 归档页批量查询

**现状证据**

| 位置 | 当前行为 |

### 8.2 数据模型、规则发布与换届

- `ScoreRuleSet` 保存规范化规则 JSON、计算契约版本、初始或导入来源、发布者和发布时间。`(tournament_id, version)` 唯一，发布记录不可改写。本届最新发布版本为生效版本。后续发布时由服务端递增版本，与审计同事务。恢复旧配置时复制成新版本。
- `MatchCalculatorResult` 按整场保存锁定的规则版本，并分别存放 A、B 双方的原始计分明细。双方可先后补齐，已提交明细及整场版本不可改写。两组联合外键保证比赛和规则都属于同一赛季。既有 `player_a_score`、`player_b_score` 仍保存未乘难度倍率的整数。迁移保留现有手填成绩和审计，原有整场按需加入计分器明细。
- 正式整场第一次成功提交计分器成绩时绑定该届生效版本。绑定前遇到页面版本过期，返回 409 并提示复核、刷新；绑定后双方均用该整场锁定版本。已有规则更新不会改动已绑定场次；发布与首次提交同时发生时，按现有写入锁顺序校验和提交。弃权自动补零沿用既有逻辑，首次真实成绩提交才绑定版本。
- 换季向导要求明确选择计分器配置。超级管理员可上传独立版文件并预览，校验失败可重选或跳过。管理员可选择「跳过，使用初始配置」继续换届。两条路径都与换季同事务写入新届第 1 版，并记录来源。换届后由超级管理员补导入并发布新版。往届和已锁定规则的整场沿原版本复核。
- schema 9 加入用于约束整场归属的索引及两张计分器表。通过显式 `prepare` 升级到 schema 10 时，先备份，再为赛季增加 `calculator_enabled`。现有及新建赛季默认关闭，原有比赛无需回填计分器数据。已绑定计分器的整场继续沿用该版本，已提交手填成绩的整场继续手填。

### 8.3 超管规则配置通道

- **共用配置格式**。以独立版 `buildConfigJson()` 的实际输出为准，顶层字段为 `app`、`kind`、`version`、`exportedAt`、`config`。`app` 为 `arknights-ir-score-calculator`，`kind` 为 `config`。首期兼容现有 v3 文件。导出文件中的 `version` 和 `config.version` 属于独立版配置，赛季发布版本由网站单独分配。识别到计分明细 JSON 时提示改用「导出配置」。
- **共用规则正文**。校验通过后保存并向站内版注入导出文件中的 `config`。保留 `basic`、`levelBonus`、`extraBonus`、`penalty` 四分区及分组、条目、显示字段、分值和原有顺序。用时区间按文件顺序判定，支持 `ceil`、`exact`；`timeRules: []` 表示用时不计分，空分组也可导入。以该正文作为超管预览、选手预览和服务端重算的共同输入。

计分按十进制运算，区间含两端并按配置顺序取首个匹配，空用时不计分，数量按下限钳制。浏览器将全角输入归一化，重算接收规范化的十进制字符串、布尔值和配置中的条目 ID。先按完整精度累计，再将总分保留两位小数，恰好半单位时向正无穷方向取整，例如 1.235 得 1.24，−1.235 得 −1.23。整场原始成绩按同方向将两位小数总分取整，再交由现有难度倍率和结算流程处理。

## 10. 明确不做

- 多场赛事**并行**运行（`Setting` 保持全局单例，同一时刻只有一个 `is_active=True` 的赛事）；需要并行时复制实例部署，而不是改模型。
- 更换玩法（非赛道模型、不同队伍/位置结构）；`Roguelike` 与两名自定义字段是数据结构，不是配置项。
- 重写前后端框架、引入前端构建链（Vue/React/Webpack 等）。
- 表演赛专项暂缓：不补齐创建/展示入口、不决定其积分和胜负规则，不将其作为 P0–P3 发布阻断项；通用归档写保护仍覆盖所有已有记录。
- 为 `/history` 做跨届汇总统计看板（当前只要求列表与详情可用）。
- 引入缓存层（Redis 等）来解决归档页性能；先用聚合查询把 N+1 消掉。

### 11.2 澄清结果与实现边界

**本轮已提出的业务选择均已答复，目前没有待用户确认项。** 表演赛/分时对阵、轮空、管理员结束入口和队伍倍率已先按源码解释；用户随后确认分时整场一次、确认结束才计分、弃权补交/零分、并列跳号、驳回不撤分，以及人工调整先计队员再乘队伍倍率。

P1-5 记录现有“修改 → 确认修改”实际承担首次结束和计分的路径，以及“审核通过”不能替代结束的现状；P1-6 记录赛季队伍倍率的含义、默认值与已确认公式。相关命名/状态改造是待实现要求，不能写成已经存在一个独立的“确认结束”按钮。

以上是业务规则确认，不是实现验收。旧数据归属、原始历史规则、曾独立计分的分段及未知人工差额仍按相应迁移清单人工核对；这类数据核对不等于本轮政策尚未决定。实施中如发现新的业务歧义，须列具体场景另行提问，不擅自扩展已确认范围。
