## 1. 结论摘要

1. **「换赛事」已经做到改配置不改代码**，赛事名、术语、队制、赛制默认值、品牌色、赛季模型、往届归档均已参数化；剩下的问题不是「换名」，而是**换季时的一致性**。
2. **换季会误伤往届数据**：积分重算全表清零、遍历所有已完成比赛，且用**当前**赛道难度参数换算（`scoring.py:70-133`）。换届后调整难度或点「重置积分」，历史积分会被按新规则改写。
3. **换季的原子性依赖唯一一次提交**：`new_season()` 在末尾提交一次（`app.py:3272`），但 `Setting.get_instance()` 自身会 `commit()`（`app.py:670-677`），首次建 `Setting` 时会提前提交一次；加上没有预检与幂等，重复点按仍可能产生多个新赛季。报名/比赛时间、晋级数等配置也不继承，每届必须人工重填。
4. **数据库迁移只在 SQLite 生效且异常静默**：`_migrate_schema()` 直连 `.db` 文件（`app.py:4271-4277`），补列清单不含赛季相关列，`except` 仅打印（`4309-4310`）；`gunicorn --workers 4`（`docker-entrypoint.sh:27-33`）下四个进程会并发执行迁移。
5. **赛季隔离已收敛但有漏点**：选手胜负统计跨届累计（`app.py:1866-1868`、`1935-1937`）、`JoinRequest` 无赛季维度（`1709-1711`）、按 id 直取的详情页无赛季校验（`1164`、`2360`、`2611`）。
6. **计分器可以集成，但不能直接替换手填输入**：`arknights-score-calculator` 是纯离线单文件，读不到服务端规则；且「删掉页面上改规则的按钮」不等于不可改——`window.__scoring` 仍暴露可写引用。必须做到「超管定义规则 + 服务端注入 + 提交后服务端重算」三件事同时成立。

## 3. P0 往届数据安全

> 本节为本次改造重点，逐条给出「现状证据 → 触发场景 → 改法 → 验收」。

### 3.1 P0-1 积分重算按赛季隔离

**现状证据**

| 位置 | 当前行为 |
|---|---|
| `scoring.py:86-94` | `TeamMember.query.all()` / `Team.query.all()` **全表清零** |
| `scoring.py:96-99` | 遍历**所有** `finished` / `forfeit_a` / `forfeit_b` 比赛 |
| `scoring.py:107-118` | 按 `roguelike` key 取**当前**赛道配置换算倍率 |
| `scoring.py:133` | 函数内部自行 `commit()`，把事务边界写在库函数里 |
| `app.py:3183` | `POST /admin/reset-scores` 直接调用 |
| `app.py:3493` | 管理员改分后调用（`3486` 注释：通知必须先建，因为重算内部会 commit） |
| `app.py:4102` | 弃权流程调用 |
| `app.py:688` | `Match.tournament_id` 已存在，可直接用于过滤，无需加列 |
| `app.py:447-448` | `Tournament.teams` / `Tournament.matches` 关系已存在 |

**触发场景**

- 换届后调整赛道难度 → 点「重置积分」→ **往届所有队伍与队员积分按新参数重写**，`/history` 榜单跟着变。
- 管理员修改一场旧赛季比赛的结果 → 触发全库重算，旧赛季积分同样漂移，且耗时随累计比赛数线性增长。

**改法**

1. 签名改为 `recalculate_all_scores(tournament_id=None)`：`None` 时取 `Tournament.get_active()`；仍无则直接返回（空库不报错）。
2. 清零范围按赛季收窄：`Team.query.filter_by(tournament_id=tid)`；队员用 `TeamMember.join(Team).filter(Team.tournament_id == tid)`。
3. 比赛范围加 `Match.tournament_id == tid`；`_update_team_scores(match)` 改为 `recalculate_all_scores(match.tournament_id)`。
4. 移除 `scoring.py:133` 的内部 `commit()`，由调用方（`reset_scores` / `edit_match_result` / 弃权流程）统一提交；同时删掉 `app.py:3486` 那条「必须先建通知」的隐式约束注释。
5. **历史数据兼容**：`matches.tournament_id IS NULL` 的比赛不会被任何赛季命中。**已定采用「人工确认清单」**：脚本按「`team_a.tournament_id` → `team_b.tournament_id` → `created_at` 落在赛季区间」推算出建议值，只输出报告（比赛 id、双方、建议赛季、推断依据），**不直接写库**；人工核对后再执行写入，脚本可重复执行。当前数据核查：主库 0 场比赛，备份库 3 场且全部带 `tournament_id`，暂无需要回填的行。
6. 后台「重置积分」增加作用域提示（当前赛季 / 指定届），避免误操作。

**验收**

- 造两届数据：切到新赛季、改难度、点重置 → `/history/<旧届>` 的队伍榜与队员榜数值不变。
- 对旧赛季某场比赛执行「修改结果」→ 只有该届队伍积分变化，新赛季不受影响。
- 空库（无 `Tournament`）调用 `recalculate_all_scores()` → 正常返回，不抛异常。
- 重算后 `SystemLog` 记录本次作用域（届数 + 队伍数 + 场次数）。

**工作量 / 风险**：小 / 中。风险集中在历史 `tournament_id` 为空的回填，回填规则必须先与运营确认。

### 3.2 P0-2 倍率快照

**现状证据**

| 位置 | 当前行为 |
|---|---|
| `app.py:471-473` | `Roguelike.difficulty_min` / `difficulty_max` / `difficulty_step` 全局共享、可按赛季修改 |
| `app.py:476-478` | `get_multiplier()` 每次实时读取当前参数 |
| `app.py:695-696` | `Match` 只存 `player_a_difficulty` / `player_b_difficulty`，**不存倍率、不存最终分** |
| `scoring.py:110-118` | 重算时用当前 `Roguelike` 重新换算 |
| `scoring.py:125-131` | 队伍分 = 队员分之和 × 该赛季 `bonus`（`bonus` 已按赛季隔离） |

**触发场景**

- 难度阶级从 `0.1` 调到 `0.2` → 所有历史场次的倍率被重新解释，历史积分改变且无法复现原值。
- 赛道被删除后 `rl` 为 `None` → 倍率退化为 `1.0`（`scoring.py:112`），历史成绩静默变低。
- 争议复盘时无法说明「当时按什么倍率算的」。

**改法**

1. `Match` 增两列：`player_a_multiplier`、`player_b_multiplier`，类型用 `db.Numeric(8, 4)`（不用 `Float`，避免累加误差）。
2. 写入时机：重算时若快照为空则写入，之后**永不覆盖**；`edit_match_result` 中修改 `difficulty` 或分数时（`app.py:3469-3472` 之后）显式置 `None`，强制下一次重算重取。
3. 重算优先级：有快照用快照 → 无快照才调 `Roguelike.get_multiplier()` 并回写。
4. 可选冗余列 `player_a_final_score` / `player_b_final_score`（`int(raw * multiplier)`），用于排行榜与明细对账；与 `scoring.py:29-31` 的截断口径保持一致。

**验收**

- 记录某历史场次当前积分 → 把 `difficulty_step` 从 `0.1` 改为 `0.2` → 重置积分 → 该场次及所属队员总分不变。
- 新赛季新比赛按新参数计算，快照值与 `Numeric` 精度一致（如 `1.2000`）。
- 快照为空的旧数据重算一次后自动补齐，二次重算结果幂等。
- 后台比赛详情能看到该场的倍率与最终分，便于复核。

**工作量 / 风险**：小 / 中。风险是取整口径（先乘后截断）必须与现有 `calculate_final_score()` 一致，否则排行会出现 ±1 差异。

### 3.3 P0-3 迁移正规化与启动期并发

**现状证据**

| 位置 | 当前行为 |
|---|---|
| `app.py:4271-4277` | 直连 `DB_FILE`（`sqlite3.connect`），**MySQL 部署完全不执行** |
| `app.py:4281-4294` | 补列清单仅 12 项，缺 `teams.tournament_id`、`matches.tournament_id`、`tournaments`、`carousel_items`、`rules` |
| `app.py:4217-4268` | `_migrate_teams_unique()` 建新表重建 `teams`；`4262-4263` 的 `SELECT` 依赖 `tournament_id` 列已存在 |
| `app.py:4309-4310` | `except Exception` 仅 `print` 后关闭连接，**迁移失败不阻断启动** |
| `app.py:4400-4403` | `create_all()` + `_migrate_schema()` 在模块级 `create_app()` 内执行 |
| `docker-entrypoint.sh:27-33` | `gunicorn --workers 4 app:app` → 4 个进程**并发**执行建表/迁移 |
| `app.py:129`、`4329` | `Migrate` 已初始化，但仓库无 `migrations/`，从未 `flask db init` |
| `docker-compose.yml` | 默认 MySQL，与「迁移只支持 SQLite」直接冲突 |

**触发场景**

- MySQL 部署：老库升级后新列不存在 → 查询/写入直接报错，且启动日志无任何提示。
- 4 个 worker 同时重建 `teams` → `table teams_new already exists`、数据被并发覆盖。
- 迁移中途失败被吞 → 结构停留半成品，问题延后到业务请求才暴露。

**改法（两级，本批只做最小闭环）**

1. 用 `sqlalchemy.inspect(db.engine)` 取代 `sqlite3` 直连，列定义从模型 `__table__.columns` 派生（不再手写清单），SQLite / MySQL 同一套逻辑。
2. 新增 `schema_version(version, applied_at)` 表，迁移按版本号幂等推进；已存在的列跳过。
3. 失败即 `raise` 并终止进程（fail-fast），日志输出表名、列名、原始异常；不允许「打印警告后继续」。
4. 单进程执行：`docker-entrypoint.sh` 在 `exec gunicorn` 之前先跑一次迁移命令（`flask db upgrade` 或独立脚本），成功后再启动多 worker；纯 SQLite 本地开发可用文件锁或 `BEGIN IMMEDIATE` 兜底。
5. 迁移前备份：SQLite `shutil.copy2(DB_FILE, DB_FILE + f'.bak.{ts}')`，保留最近 5 份；MySQL 至少输出「请先 mysqldump」的显式阻断提示，或配置开关执行 dump。
6. 顺序保证：`_migrate_teams_unique()` 依赖 `tournaments` 表已存在（`app.py:4230-4234`），必须排在 `create_all()` 之后；MySQL 无 `PRAGMA foreign_keys`，需分支处理。

**为什么不用已初始化的 Flask-Migrate（留好切换点）**

`Migrate` 已经在 `app.py:129`、`4329` 完成初始化，但仓库没有 `migrations/` 目录，从未 `flask db init`，等于**没有迁移基线**。本批仍然自研 `schema_version`，取舍如下：

| 维度 | 直接接 alembic | 本批自研 `schema_version` |
|---|---|---|
| 起点 | 无 `migrations/`，需先建基线 | 无历史包袱 |
| 老库 | 模型与线上结构本身不一致（缺列），自动生成的 diff 不可信；`stamp` 到哪个版本要先摸清实际结构 | 以「模型列 vs 实际列」为口径，缺什么补什么，天然适配不一致的库 |
| 运维 | 需在部署流程显式执行 `flask db upgrade`，多 worker 下还要保证只跑一次 | 启动自愈，无额外步骤 |
| 能力 | 支持 downgrade、分支、revision 历史 | 只支持向前补列，无回滚 |
| 适用 | 结构频繁演进、多人协作 | 单实例、表数量有限、一次性补列 |

结论：**当前阶段自研，但不封死后续路径**。`schema_version` 与 alembic 的 `alembic_version` 可以并存；若将来 schema 变更变频繁，执行 `flask db init` + `flask db stamp head` 建立基线后即可切换，届时删除自研迁移函数即可，不需要重做历史 revision。

**验收**

- 用旧库副本启动：缺失列被补齐，`schema_version` 有记录，`teams` 唯一约束为 `(tournament_id, team_name)`。
- 故意制造迁移失败 → 进程退出码非 0，日志可直接定位到表/列，容器不会带病提供服务。
- MySQL 环境启动后 `SHOW COLUMNS FROM matches` 含 `tournament_id`。
- 4 worker 并发启动 → 无 `already exists` 类错误，无重复建表。

**工作量 / 风险**：中 / 高。改动的是启动路径，必须在数据库副本上完整演练一遍再上线；建议保留旧版镜像以便回滚。

### 3.4 P0-4 换季事务化、前置校验与备份

**现状证据**

| 位置 | 当前行为 |
|---|---|
| `app.py:3241-3243` | 取 `Setting` 与 `Tournament.get_active()`，届数直接 +1 |
| `app.py:3247-3250` | 旧赛季置 `is_active=False`、状态改 `finished` |
| `app.py:3252-3259` | 删除旧赛季队伍的 `pending` 邀请与加入申请 |
| `app.py:3260-3264` | 新建赛季，**只继承 `bonus_score`** |
| `app.py:3266-3267` | 批量把非管理员的 `User.status` 归零（**全表写**，不区分是否本届参与者） |
| `app.py:3268` | `TimePreference.query.delete()` 清空全部时间意愿 |
| `app.py:3269-3271` | 改 `Setting.tournament_name`、`advance_count=0`、`registration_open=True` |
| `app.py:3272-3273` | 唯一一次 `commit()`，随后才写 `SystemLog` |
| `app.py:452-454` | `get_active()` 用 `.first()`，无排序、无唯一性保护 |

**澄清一个判断**：单次 `commit()` 已经保证「要么全成、要么全不成」的原子性（异常时请求结束会回滚）。真正的缺口是**缺预检、缺幂等、缺备份、日志与业务不同事务、脏数据下取到哪条 active 不确定**。

**触发场景**

- 页面卡顿或手滑连点两次「开启新赛季」→ 产生两个新赛季，榜单随机命中其中一个。
- 上届还有未完成的比赛就换季 → 那些比赛永久停留在旧赛季且无法收尾。
- 换季成功但日志写入失败 → 事后无法追溯谁在何时换的届。
- 库里存在多条 `is_active=True`（历史遗留）→ `get_active()` 返回哪条不确定，全站数据跟着漂。

**改法**

1. **预检**（提交前）：
   - `Tournament.query.filter_by(is_active=True).count() != 1` → 拒绝并提示先修复。
   - 未完成比赛：`Match.query.filter_by(tournament_id=current.id).filter(Match.status.notin_(['finished', 'forfeit_a', 'forfeit_b'])).count()` → 默认拒绝，需勾选「强制换季」才继续。
   - 同名或同届已存在 → 拒绝。
2. **幂等**：`Tournament` 增加 `UniqueConstraint('season_number')`（或 `(name)`），重复提交由数据库兜底；捕获 `IntegrityError` 转成友好提示。
3. **备份前置**：调用 P0-3 的备份函数；备份失败则中止，不做任何写入。
4. **事务与日志**：`try / except: rollback + raise`；`log_system_action` 与业务同事务提交（或独立事务且失败可重试），保证「有换季必有日志、失败必无半状态」。
5. **重置项显式化**：把「必然重置」的字段写成常量列表（`advance_count=0`、`registration_open=True`、`TimePreference` 清空、非管理员 `status=0`），并在页面提示；`team_size` / `allow_incomplete_teams` 当前是「保留上届值」，先保持现状并注明，是否改为可勾选继承放到 P1-1。
6. **审核流程：已定删除**（D1=②）：`approval_status`（`app.py:493`）从不参与准入判断——`is_approved()`（`app.py:536-537`）全仓 **0 处调用**，登录、建队、报名都不校验；后台「审核通过/拒绝」（`app.py:3345-3374`）只改字段并写一条无人查看的通知。因此当前并不存在「上届被拒用户本届被拒」，他们照常参赛。处理方式：
   - 删除 `approval_status` 字段（需迁移）、`/admin/approvals`（`3331-3342`）、`approve_user` / `reject_user`（`3345-3374`）、`admin/approvals.html`、`is_approved()`；
   - 注册后直接可用，报名改为直接生效；
   - 换季不再需要讨论 `approval_status` 口径，`User.status` 归零即可；
   - 复用指南里「注册 → 待审核 → 通过」的流程描述同步删除。
7. **批量更新前统计**：`User.status` 归零前先 `count()` 受影响行数并写入日志，便于事后核对。
8. `get_active()` 改为 `order_by(created_at.desc(), id.desc()).first()`，降低脏数据下的不确定性。

**验收**

- 连续 POST 两次 → 只产生一个赛季，第二次收到「该届已存在」提示。
- 存在未完成比赛时点换季 → 被拒绝并给出数量；勾选强制后可继续，且未完成比赛仍在旧赛季。
- 人为制造提交失败（临时唯一约束冲突）→ 旧赛季仍 `is_active=True`、无新赛季残留、pending 邀请与申请未被删除。
- 换季后 `SystemLog` 恰好一条 `new_season`，内容含新旧届数与影响用户数。
- `/history` 届数、榜单与首页统计在新旧赛季之间切换正确。

**工作量 / 风险**：中 / 中。风险点是预检过严会阻断正常换季，建议「未完成比赛」默认警告 + 强制开关，而不是硬性禁止。

### 3.5 P0 实施顺序（有依赖，不能并行）

```
P0-3 迁移与备份    ← 提供补列能力与备份函数，是其它三项的基础
      ↓
P0-2 倍率快照      ← 需要 matches 新列
      ↓
P0-1 按赛季重算    ← 依赖快照列；两者一起上线，避免「先隔离后无快照」的中间态
      ↓
P0-4 换季事务化    ← 依赖备份函数与 get_active 收敛
```

**为什么这个顺序**：P0-1 与 P0-2 必须同批发布。若只按赛季隔离而未加快照，历史积分仍会随赛道参数漂移；若只加快照而未隔离，重算仍会覆盖往届。两项完成后，换季改造才有意义。

**目标形态（三层权威，缺一层都等于没做）**

```
超管提交 JSON → ScoreRuleSet（服务端唯一真相，按赛季 + 版本）
        ↓ 服务端渲染时内联注入（不发起二次请求）
计分器页面（规则只读，可计分，不可改规则）
        ↓ 提交「原始输入 + 明细 + 规则版本」
服务端用同版本配置重算 → 与客户端总分比对 → 落库（分数 + 明细 + 版本）
```

| 层 | 解决什么 | 缺失后果 |
|---|---|---|
| 服务端规则集 | 规则由谁定义 | 选手本地改配置即可加分 |
| 注入渲染 | 页面怎么拿到规则 | 静态页读不到规则，只能回退内置默认值 |
| 服务端重算 | 提交的数字可不可信 | 删再多按钮，F12 仍可伪造分数 |

### 8.2 数据模型

| 对象 | 字段 | 说明 |
|---|---|---|
| `ScoreRuleSet`（新表） | `id, tournament_id(FK), version(Int), config(Text), uploaded_by(FK), is_active(Bool), created_at` | 与 `tournament_id` 联合唯一 `(tournament_id, version)`；同一赛季仅一条 `is_active=True` |
| `Match` 扩展 | `player_a_detail(Text), player_b_detail(Text), player_a_rule_version(Int), player_b_rule_version(Int)` | 明细存原始输入 + 重算结果；版本用于冻结历史 |
| 复用列 | `Match.player_a_score / player_b_score`（`706-707`） | 仍存**原始成绩**（未乘倍率），与现有公式一致 |

要点：

- `config` 存 JSON **原文**，不解析进关系表——规则条目数量与结构会变，解析成表会引发频繁迁移。
- `version` 由服务端递增，不接受客户端指定（防止重放旧版本）。
- 明细用 `Text` 存 JSON；列表页不解析，只在详情页按需读取，避免 N+1。

2. 服务端校验（**不能只靠前端**，否则一条坏配置会让全员无法计分）：

### 8.5 提交与服务端重算

**载荷**

```
{
  "match_id": 123,
  "rule_version": 4,
  "score": 1580,
  "detail": {
    "scores": {"original": "1200", "time": "3.5", "items": {"lv-1": true, "ex-recruit-6": "2"}},
    "result": {"original": 1200, "bonus": 380, "penalty": 0, "total": 1580}
  }
}
```

**处理顺序**

1. 校验登录态与选手身份（A 还是 B），复用 `app.py:4136-4141` 的判断。
2. 校验 `rule_version` 与该场所属赛季的生效版本一致；不一致则拒绝并提示刷新。
3. 校验 `detail.scores` 结构：只接受配置中存在的条目 id，忽略其余字段。
4. 用 `score_engine.compute_totals(config, scores)` 重算（Python 复刻 `computeTotals`）。
5. 与客户端 `score` 比对（容差 0）；不一致则 400 并返回逐项差异。
6. 通过后写入：`player_x_score = round(total)`、`player_x_detail = detail JSON`、`player_x_rule_version = rule_version`；截图与难度沿用现有逻辑（`app.py:4153-4172`）。
7. `ScoreLog` 留痕（管理员后续改分仍走 `3426-3497`）。

**必须一起改的现有缺陷**

| 问题 | 现状 | 改法 |
|---|---|---|
| 小数静默丢失 | `request.form.get('score', type=int)`（`4145`）遇到 `1500.5` 返回 `None` | 改 `type=float` 后 `round()` |
| 0 分被丢弃 | `if score:`（`4179`、`4187`） | 改 `if score is not None` |
| 负分被前端拦下 | `submit_result.html:46` 的 `min="0"`、`admin/matches.html:117-121` | 按规则是否允许负分决定放开或后端校验 |
| 语义混淆 | 计分器的「最终得分」= 主站的「原始成绩」，之后还要乘倍率 | 页面文案改为「计分总分（未乘难度倍率）」 |

### 8.6 验收与风险

**验收**

- 超管上传合法 JSON → 新版本生效，旧版本转为历史可查；普通管理员访问该页被拒。
- 上传缺 `penalty` 分区的 JSON → 拒绝并指出具体字段，页面不崩。
- 选手打开计分器 → 规则与服务端一致；页面无任何改规则入口。
- 正常计分提交 → 分数与明细落库，`rule_version` 正确。
- 篡改请求中的 `score`（如改成 99999）→ 服务端重算不一致，返回 400。
- 超管发布新版本后 → 旧比赛重算仍按旧版本，历史成绩不变。
- 同时提交 0 分、负分（规则允许时）→ 正确落库，不被 `if score:` 丢弃。
- 同一选手重复提交 → 按现有「已提交过结果」逻辑拒绝（`4175-4177`）。

**风险**

| 风险 | 说明 | 缓解 |
|---|---|---|
| JS/Python 双实现漂移 | 同一份输入两边算出不同结果 | 用同一批用例对拍（`tests/test_score_engine.py`），覆盖时段边界、阈值、空值、全角数字 |
| 坏配置影响全员 | 解析失败导致页面空白 | 服务端校验 + 保存前预览 + 保留上一版本可回滚 |
| 权限绕过 | 普通管理员改规则 | 视图内 `is_super_admin()` 二次校验 + 审计日志 |
| 规则条目变动导致旧明细不可读 | 旧 `scores` 的 id 在新配置中不存在 | 明细绑定 `rule_version`，按版本读配置 |

**工作量 / 风险**：大 / 中。

> 前置：第 8 章的注入能力必须先就位，否则删掉本地配置后页面只能退回 `BUILTIN_CONFIG`，超管通道形同虚设。

### 9.3 localStorage 改造

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | `loadConfig()` 只返回「服务端注入配置 + 内置兜底」，不读不写 `localStorage`；启动时清理一次旧键 | 单一真相，彻底断后路 |
| B | 保留读取，只是编辑器不再写 | ❌ 无效：旧存档仍会覆盖服务端配置（`计分器:414` 的版本比较） |
| C | 改用 `sessionStorage` 存计分草稿 | 与本议题无关，属独立需求（防刷新丢输入），不建议混入 |

选 A 后连带删除：

- `STORAGE_KEY` / `EMBED_SIG_KEY`（`计分器:350-351`）
- `loadConfig()` / `saveConfig()`（`397-427`）
- `embeddedSignature()`（`389-395`）——只服务于「内嵌配置变了才优先」的判断，本地存储移除后无意义
- `let config = loadConfig()`（`429`）改为「构造 → 深冻结」
- `计分器:353-357`、`408-409` 的注释（描述已失效）

**兼容**：老用户浏览器里残留的 `arknights-ir-score-calculator.config.v1` 不会自动消失，页面启动时主动 `removeItem` 一次，避免将来有人恢复读取时旧规则「复活」。

**保留** `EMBEDDED_CONFIG` 通道（`计分器:336-348`），它是第 8 章注入规则的最小改动路径。

### 9.4 调试接口收敛

`window.__scoring`（`计分器:1498-1527`）当前暴露大量写能力，其中 `1499` 的 `get config() { return config; }` 返回**引用**——控制台执行 `__scoring.config.penalty.groups[0].items[0].score = 999` 再 `updateScores()` 就能刷出任意分。

改法（两条都要做）：

1. 移除写入口：`saveConfig`、`applyImport`、`applyConfigImport`、`buildConfigJson`、`buildCustomHtml`、`resetConfig`。
2. 规则不可变：`config` 改为深冻结（`Object.freeze` 递归），或 getter 返回 `deepClone(config)`；`setMeta` 可保留（只改页头文本，不参与计分）。

### 9.6 验收与实施顺序

**验收**（浏览器可直接执行）

1. 页面不存在「修改配置 / 导出配置 / 导入配置 / 导出定制 HTML」按钮。
2. `Object.keys(window.__scoring)` 不含 `saveConfig` / `applyImport` / `applyConfigImport` / `buildConfigJson` / `buildCustomHtml` / `resetConfig`。
3. `__scoring.config.basic.groups[0].items[0].score = 999; __scoring.updateScores()` → 总分**不变**。
4. 手工写入旧 `localStorage` 键后刷新 → 键被清除，配置仍是服务端版本。
5. 篡改页面内 `<script id="default-config">` 后刷新 → 恢复服务端值。
6. 注入缺 `penalty` 的配置 → 正常回退内置兜底，不白屏。
7. 导出 CSV、打印/PDF、清空计分、录入计分无回归。

**实施顺序（不可颠倒）**

```
第 8 章注入能力（规则集 + 超管通道 + calculator 路由）
   ↓
第 9 章删改（编辑器、导入导出、本地存储、调试接口）
   ↓
提交与服务端重算收尾（8.5）
```

理由：先删本地配置再补注入，会让页面在中间版本退回 `BUILTIN_CONFIG`，选手用的规则与超管配置不一致。

**工作量 / 风险**：中 / 中。主要是删改量（约 350 行净减少）与「删除不彻底」的风险——建议用 grep 反向验证 `saveConfig|applyImport|buildCustomHtml|localStorage` 在产物中为 0 命中。

## 10. 明确不做

- 多场赛事**并行**运行（`Setting` 保持全局单例，同一时刻只有一个 `is_active=True` 的赛事）；需要并行时复制实例部署，而不是改模型。
- 更换玩法（非赛道模型、不同队伍/位置结构）；`Roguelike` 与两名自定义字段是数据结构，不是配置项。
- 重写前后端框架、引入前端构建链（Vue/React/Webpack 等）。
- 把计分器改写成 Jinja 模板（会与离线单文件版双维护）；采用「静态资源 + 服务端注入配置」的拆分方式。
- 为 `/history` 做跨届汇总统计看板（当前只要求列表与详情可用）。
- 引入缓存层（Redis 等）来解决归档页性能；先用聚合查询把 N+1 消掉。
