# 复用指南：把本系统用于新的赛事

> 本文件与 [README](../README.md) 描述当前可操作功能。需求以 [已确认决策](每赛季复用改造建议.md#11-决策记录与待确认项) 和 [改造最终参考](改造最终参考.md) 为准，实现进度以代码和验收记录为依据。[初版需求 00–19](../冷水坑杯3-项目需求文档-初版/00-项目概述.md) 留作历史设计资料。
> 目标：**换赛事只改配置与素材，不改代码**；凡是仍必须改代码的地方，都在[第 5 节](#5-仍写死在代码里的内容)集中列出。

---

## 1. 先选场景

**项目定位（已确认的范围）**：单实例、一次只跑一场赛事；赛道/玩法沿用「肉鸽」这一套模型。以下两类需求**明确不在范围内**，不需要为其做改造：

- 多场赛事**同时**运行（`Setting` 保持全局单例）
- 换玩法（非肉鸽赛道、不同队伍/位置模型）

| 场景 | 做法 | 是否需要改代码 |
|---|---|---|
| **A. 同一赛事办下一届** | 后台「赛事设置」→「开启新赛季」 | 否 |
| **B. 换一场赛事（同玩法，实例级替换）** | 改环境变量 + 后台设置 + 换素材 | 否 |
| **C. 二次开发** | 见[第 7 节](#7-可复用资产清单别重写) | — |
| ~~换玩法~~ | 不支持；术语变量可改文案，但模型仍按「赛道 + 两名自定义字段」设计 | — |
| ~~多赛事并行~~ | 不支持；同一时刻只有一个 `is_active=True` 的赛事 | — |

## 2. 配置优先级（唯一真相规则）

所有"赛事级"配置按下列顺序取值，**上层有值就不再往下找**：

```
数据库设置（后台「赛事设置」/ Setting / Tournament）
        ↓ 为空
app.config（即环境变量）
        ↓ 为空
代码默认值
```

对应实现：

| 读取函数 | 数据库来源 | 环境变量 | 代码默认 |
|---|---|---|---|
| `get_event_name()` | 往届快照或当前 `Tournament.name`，`Setting.tournament_name` 仅兼容回退 | `TOURNAMENT_NAME`（缺省由 `EVENT_NAME` + `SEASON_NUMBER` 拼出） | `赛事管理系统` |
| `get_team_size()` | `Setting.team_size` | `TEAM_SIZE` | `4` |
| `get_team_positions()` | — （暂不支持后台改） | `TEAM_POSITIONS` | `cold,normal1,normal2,pit` |
| `get_labels()` | — （暂不支持后台改） | `TRACK_LABEL` / `MEMBER_FIELD1_LABEL` / `MEMBER_FIELD2_LABEL` | `肉鸽` / `分队` / `开局干员` |
| `get_tournament_status()` | 活跃赛事的 `Tournament.status` | — | 无活跃赛事时显示 `registration` |
| 会话签名密钥 | — | `SECRET_KEY`，生产必填 | 开发环境生成临时随机密钥并告警 |
| 管理员口令 | 已有账号按 `User.password_hash` 校验 | `ADMIN_PASSWORD` 供空赛事库初始化，生产必填。初始超管另用 `SUPER_ADMIN_PASSWORD` | 初始口令须配置 |
| 赛制默认值 | — | `SCHEDULE_*` / `DEFAULT_*` | 见 [第 5 节](#5-仍写死在代码里的内容) |
| 品牌主色 | — | `BRAND_PRIMARY_COLOR` | `#0d6efd` |

统一实现：`_resolve_config(config_key, env_key, default, db_getter)` —— 新增配置项请复用它，不要再手写 `try/except RuntimeError`。

模板侧一次注入：`event_name` / `labels.track|field1|field2` / `team_size` / `theme.brand_color` / `current_season.name|number`。
品牌色通过 CSS 变量 `--brand-primary` 生效（导航、按钮、卡片边框、`.bg-primary`/`.border-primary` 等已跟随）。

> 赛事名以当前 `Tournament.name` 为准。创建新赛季和后台改名都写入该字段。管理赛事阶段也统一写入 `Tournament.status`。

开发环境缺少 `SECRET_KEY` 会使用临时随机密钥，重启后需重新登录。生产入口缺少 `SECRET_KEY` 或 `ADMIN_PASSWORD` 会停止启动。已知默认配置会记录告警。既有账号按数据库中的密码继续登录，管理员若仍使用旧版默认口令或临时重置口令，会在后台首页看到改密提示。注册完成即可登录。

## 3. 换赛事操作清单（场景 B）

### 步骤 1：环境变量

复制一份 `.env`（或修改 `docker-compose.yml` 的 `environment`）。启动前填写独立的随机密钥和初始管理员口令。原生部署需把这些配置导出到进程环境。

```ini
EVENT_NAME=新赛事名
SEASON_NUMBER=1
TEAM_SIZE=4
TEAM_POSITIONS=cold,normal1,normal2,pit
TRACK_LABEL=肉鸽
MEMBER_FIELD1_LABEL=分队
MEMBER_FIELD2_LABEL=开局干员
PORT=19199
ADMIN_USERNAME=admin
ADMIN_PASSWORD=
DATABASE_URL=          # 留空 = 使用 .db/lskb.db（SQLite）
SECRET_KEY=
```

### 步骤 2：后台设置

登录管理员 →「赛事设置」：

- 赛事名称（更新 `Tournament.name`，全站标题 / 导航 / 导出文件名同步变化）
- 队伍满员人数（留空则回退 `TEAM_SIZE`）
- 「允许未满员开赛」开关
- 报名 / 比赛时间

在「积分配置」填写队伍倍率和晋级名额，在「赛道管理」核对启用赛道及难度，在「规则管理」发布规则。在「轮播管理」维护首页素材，在仪表盘处理待办，并通过「报名控制」手动确认报名开关。

### 步骤 3：素材与上传目录

| 原生默认位置（相对项目根目录） | 用途 |
|---|---|
| `.db/lskb.db` | 默认 SQLite 数据库。可用 `DB_FILE` 指定文件，显式设置的 `DATABASE_URL` 优先。 |
| `image/` | `IMAGE_DIR`。存放轮播图片和视频，当届无条目时按文件名自然排序。 |
| `app/static/uploads/` | `UPLOAD_ROOT`。选手、队长及后台上传的头像存入 `avatars/`，队伍照片存入 `teams/`，成绩截图存入 `screenshots/`。 |

原生部署可在运行 `prepare` 和启动服务前导出同一组绝对路径。首次准备会创建缺失目录，日志列出 SQLite 数据库父目录、素材目录、上传根目录及三个子目录的实际路径。已有素材目录可以只读。更换上传根目录时，将原有文件按相同子目录迁入，已有的 `/static/uploads/…` 链接可继续使用。

两套 Compose 配置均将可写命名卷 `uploads` 挂到 `/app/app/static/uploads`，将宿主机 `./image` 只读挂到 `/app/image`。可在项目的 `.env` 中设置 `IMAGE_HOST_DIR=/srv/events/cup4/image` 指向该赛事的素材目录。后台轮播表单保存文件引用。增换素材时，把文件放入宿主机的素材目录。重建应用容器时，使用相同的 Compose 项目名以复用原卷。

同机运行多个独立赛事时，各自设置不同的 Compose 项目名、`PORT` 和 `IMAGE_HOST_DIR`。Compose 会按项目名隔离网络、上传、数据库和备份卷。同一份仓库可用不同的 `--env-file` 设置各实例。

> 首页优先使用当届的后台轮播条目，显示已启用的图片或视频，排序值越小越靠前。全部禁用会隐藏轮播。删空当届条目后，首页切回文件模式。后台轮播页会标明当前来源。
>
> 添加条目时，文件路径可填写素材目录内的相对路径，例如 `banners/cover.png`，也可用已有的 `image/` 或 `/carousel-media/` 前缀。已有上传素材可用 `/static/uploads/` 路径。换季勾选继承轮播时，新一届沿用所选条目引用的原素材文件。

### 步骤 4：准备实例数据库

- 全新实例使用独立空库，SQLite 指定新的 `DB_FILE`，MySQL 创建新数据库。运行 `prepare` 完成建表、迁移和空库初始化。
- 已有实例升级时，先停止旧服务，使用原数据库和存储路径运行 `prepare`。迁移会验证升级前备份。复用已有赛事的账号和历史记录时使用「开启新赛季」。

### 步骤 5：验证

```bash
# 1) 应用可创建（不启动服务）
python -c "from app import create_app; app=create_app('testing'); print(app.config['TOURNAMENT_NAME'])"

# 2) 启动后检查关键页面
curl -s http://127.0.0.1:19199/ | head -40            # 标题 / 导航是否已是新赛事名
curl -s http://127.0.0.1:19199/api/teams              # 队伍 JSON 是否是本届数据
curl -s http://127.0.0.1:19199/teams                  # 队伍列表是否只含本届
```

页面级冒烟顺序建议：首页 → 队伍列表 → 赛事规则 → 赛事大厅 → 排行榜 → 个人中心 → 后台仪表盘 → 日程 → 抽签。

### 原生和 Compose 部署

原生部署先导出进程环境，再用同一组设置完成准备和启动。以下是独立 SQLite 实例示例。另行导出 `SECRET_KEY` 和 `ADMIN_PASSWORD`，并将目录换成该实例的实际位置。

```bash
export FLASK_ENV=production FLASK_SKIP_DOTENV=1 DB_BACKEND=sqlite PORT=19198
export DB_FILE=/srv/lskb/cup-a/db/lskb.db
export UPLOAD_ROOT=/srv/lskb/cup-a/uploads IMAGE_DIR=/srv/lskb/cup-a/image
export STATE_DIR=/srv/lskb/cup-a/state BACKUP_DIR=/srv/lskb/cup-a/backups
export APP_VERSION="$(git rev-parse --short HEAD)"
python -m flask --app 'app:create_app()' prepare
python -m flask --app 'app:create_app()' deployment-info
gunicorn --bind "0.0.0.0:$PORT" --workers 4 wsgi:app
```

原生生产先安装 `requirements.txt` 和 `gunicorn==21.2.0`。开发使用 `python run.py`，兼容入口为 `python main.py` 和 `python app.py`，均要求先准备数据库。工厂和 WSGI worker 只加载已准备好的数据库。Compose 入口在启动 worker 前单进程执行一次 `prepare`。

原生 MySQL 使用 `DB_BACKEND=mysql`、`MYSQL_HOST`、`MYSQL_PORT`、`MYSQL_DATABASE`、`MYSQL_USER` 和 `MYSQL_PASSWORD`。独立提供的口令按原值使用，含特殊字符时用 shell 单引号保护。显式 `DATABASE_URL` 优先，直接在 URL 里填写凭据时须对保留字符做百分号编码。MySQL 备份和恢复需要 PATH 中的 MySQL 8 客户端。

Compose 按模板将明确列出的配置传给容器。从 `.env.example` 复制两份实例配置，分别填写随机密钥、初始口令和素材目录。例中 A 使用 SQLite。B 使用 MySQL，另填 MySQL 根口令、应用口令、库名和用户。配置文件中的源文件口令可用单引号保留 `$`、`#` 和 `@` 等字符。

| 实例 | 应用端口 | 宿主机素材目录示例 | Compose 文件 |
|---|---:|---|---|
| `cup-a` | 19198 | `/srv/lskb/cup-a/image` | `docker-compose.sqlite.yml` |
| `cup-b` | 19199 | `/srv/lskb/cup-b/image` | `docker-compose.yml` |

```bash
docker compose -p cup-a --env-file cup-a.env -f docker-compose.sqlite.yml up -d --build --wait
docker compose -p cup-b --env-file cup-b.env -f docker-compose.yml up -d --build --wait
docker compose -p cup-b --env-file cup-b.env -f docker-compose.yml exec -T app \
  python -m flask --app 'app:create_app()' deployment-info
```

MySQL 服务默认在 Compose 网络内监听 3306。需要宿主机连接时，添加 `-f docker-compose.mysql-port.yml`，并为每个项目设置独立的 `MYSQL_PUBLISH_PORT`。该端口绑定至宿主机 `127.0.0.1`。复用已有 MySQL 卷时，以库中现有账号和权限为准。镜像的初始库名和口令变量用于空卷初始化。

| 存储 | 实际容器位置 | Compose 来源 |
|---|---|---|
| SQLite 文件及 WAL/SHM | `/app/.db` | `sqlite_data` 命名卷 |
| MySQL 数据 | `/var/lib/mysql` | `mysql_data` 命名卷 |
| 头像、队伍照片和证据截图 | `/app/app/static/uploads` | `uploads` 命名卷 |
| 轮播及本地历史素材 | `/app/image` | `IMAGE_HOST_DIR` 只读绑定 |
| 维护锁 | `/app/.runtime` | `state` 命名卷 |
| 数据库和素材备份 | `/app/backups` | `backups` 命名卷 |

重建应用或数据库容器时沿用原项目名和存储路径。MySQL Compose 使用服务名 `mysql` 和内部端口，默认使用同一配置文件里的库名和账号。应用镜像内的 MySQL 客户端取自对应的 `MYSQL_IMAGE`。在 Compose 中，`APP_VERSION` 是构建参数，镜像标签、实际运行配置及备份清单会使用构建后的版本值。更新镜像时按代码版本设置 `APP_VERSION` 与对应的 `IMAGE_TAG`。

通过 `deployment-info` 核对实例的数据库、端口、路径、应用版本和 schema。再登录核对报名和素材，在「数据工具」创建并下载完整备份。执行恢复演练时使用空数据库和独立素材目录，连接串可由 `RESTORE_DATABASE_URL` 提供。恢复后用同版本应用核对数据和附件。操作细节见 [备份与恢复](P0实施与验证.md#备份与恢复)。

## 4. 赛道与规则的日常维护（不涉及换玩法）

系统按「赛道（肉鸽）+ 队伍/位置模型」设计，赛道本身是**数据**而不是代码，因此新增/调整赛道不需要改代码：

- 空库首次执行 `prepare` 会播种 4 个默认赛道（`water` / `sami` / `sarkaz` / `garden`）。之后在后台赛道管理页维护。被比赛、队员或历史快照引用的赛道可以停用，禁止删除或修改标识。停用后的赛道继续用于读取历史结果。
- 新建赛道的难度区间与倍率阶级来自 `DEFAULT_DIFFICULTY_MIN`、`DEFAULT_DIFFICULTY_MAX` 和 `DEFAULT_DIFFICULTY_STEP`。已建赛道可逐条编辑，已有整场成绩按比赛保存的难度区间和倍率校验。
- `TRACK_LABEL`、`MEMBER_FIELD1_LABEL`、`MEMBER_FIELD2_LABEL` 供当届页面、表单和提示使用。报名信息和比赛结果表的赛道列标题使用 `TRACK_LABEL`。原生部署设置环境变量，Compose 部署可在 `.env` 设置这些值。
- 归档页面按该届快照显示术语和赛道名称。缺少名称时显示记录中的标识并提示待核对。
- 每届开赛前在「赛道管理」核对启用、难度和每队人数上限，在「规则管理」核对主规则及相关赛道规则的发布状态。换季沿用当前编辑源，往届读取归档快照。

## 4.5 新赛季与用户数据的关系（问答）

| 问题 | 答案 |
|---|---|
| 上届数据会保留吗？ | 会。`Tournament` / `Team` / `TeamMember` / `Match` / `ScoreLog` 全部保留，仅把旧赛事标记为归档 |
| 会影响下一届吗？ | 不会影响列表与统计（已按赛季过滤）；但仍可见于"我的比赛"历史 |
| 用户要重新注册吗？ | 不用。**所有账号保留**，只需重新建队/入队 |
| 队伍要重建吗？ | 要。队伍按赛季归属，旧队伍留在旧赛季，新赛季需要新建（可同名） |
| 参赛进度（status）会归零吗？ | 会，管理员不受影响；新手引导完成状态保留 |
| 上届未处理的邀请/申请会怎样？ | 自动删除，避免点到已归档队伍 |

### 数据保留和手动清理

头像、队伍照片、比赛截图和系统日志默认保留。替换头像或队伍照片时，页面切换到新文件，旧文件留待手动处理。备份批次沿用数据工具的独立留存规则。

超级管理员在「后台管理 → 数据工具」选择清理范围。先备份，再预览文件数量和系统日志条数，核对后勾选确认。预览绑定当前操作者，有效期为 15 分钟。文件或引用变化时重新预览。

| 项目 | 手动处理范围 |
|---|---|
| 头像和队伍照片 | 清理上传目录中未被当前或往届记录引用的图片 |
| 比赛截图 | 清理能按文件名、赛季和参赛者确认归属的孤立截图。可按「保留最近 N 届」或「已审核通过的场次」筛选。所有仍被引用或归属待核对的截图保留 |
| 系统日志 | 按 UTC 创建时间删除早于保留天数的日志。清理记录包含操作者、范围和实际删除数量 |
| 成绩日志 | 永久保留，提供全量 JSON 导出 |

清理后可在数据工具查看结果提示。文件移除失败时，审计列出未删除的文件。若最终结果写入失败，按提示给出的审计编号核对原计划和存储状态，再重新预览。

## 5. 仍写死在代码里的内容

**换赛事已无需改代码**：前端文案、镜像标签、部署默认值全部参数化。

| 位置 | 处理方式 |
|---|---|
| 新手引导 `app/static/js/onboarding.js` | 赛事名 / 术语 / 页面路由从 `window.EVENT_CONFIG` 读取（由 `base.html` 注入，值来自 `event_name` / `labels.track` / `url_for`） |
| `app/static/js/carousel.js` | 仅文件头注释，已改为通用描述 |
| 后台「开启新赛季」输入框 | placeholder 改为通用文案「当前赛事名 + 新届数」 |
| `Dockerfile` | `ARG EVENT_NAME` / `ARG SEASON_NUMBER` → `LABEL description="${EVENT_NAME} #${SEASON_NUMBER} …"` |
| `docker-compose.yml` | `IMAGE` / `IMAGE_TAG` / `CONTAINER_NAME` / `MYSQL_*` 全部可用 `.env` 覆盖；模板见 [.env.example](../.env.example) |

仍属"改代码"的只有这两类（已确认不在需求内）：

| 项 | 说明 |
|---|---|
| 默认赛道清单 | `prepare` 的空库初始化播种 4 个默认赛道；运行期在后台「肉鸽管理」维护即可，只有"全新库且不想手工建"才需要改代码 |
| 队伍/位置模型 | 位置标签、赛道维度是数据结构，换玩法才需要改（明确不支持） |

赛制默认值现已全部可配置（阶段 1 完成）：

| 项目 | 环境变量 | 默认值 |
|---|---|---|
| 手动创建比赛的时段 | `SCHEDULE_SLOT_TIMES` | `14:00,19:00`（逗号分隔，可写 3 段以上） |
| 比赛分段时长（分钟） | `SCHEDULE_SLOT_MINUTES` | `120` |
| 队伍积分加成倍数 | `DEFAULT_BONUS_SCORE` | `500` |
| 赛道难度区间与倍率阶级 | `DEFAULT_DIFFICULTY_MIN` / `DEFAULT_DIFFICULTY_MAX` / `DEFAULT_DIFFICULTY_STEP` | `12` / `18` / `0.1` |
| 品牌主色 | `BRAND_PRIMARY_COLOR` | `#0d6efd` |

> 仅剩「默认晋级数量」（`Setting.advance_count`，默认 0，后台「晋级管理」可改）没有环境变量入口。

## 6. 复用边界与已知限制

### 6.1 单实例、单赛事（设计约束，非缺陷）

本项目按"一个部署只服务一场赛事"设计，`Setting` 保持全局单例，因此**同一时刻只有一个 `is_active=True` 的赛事**：

| 字段 | 约束 |
|---|---|
| 赛事名称 | 当前以 `Tournament.name` 为准，`Setting.tournament_name` 用于旧数据回退 |
| `team_size`、`advance_count`、`registration_open`、`allow_incomplete_teams` | 全局共享，不区分赛事 |

`Roguelike`、`Rule` 也没有 `tournament_id`——它们被视为"这套玩法的配置"，跨届沿用。

> 需要同时办两场赛事时，正确做法是**再部署一个实例**（复制 `.env` + 设置 `COMPOSE_PROJECT_NAME` / `PORT` / `CONTAINER_NAME` / `IMAGE_TAG`），而不是在同一实例内并行。

### 6.2 赛季隔离现状（已收敛）

统一入口：

| 函数 | 用途 |
|---|---|
| `active_team_query()` | 当前赛事队伍查询，无活跃赛事时为空 |
| `active_match_query(*criteria)` | 当前赛事**父比赛**查询，可追加 `status` 等条件 |
| `in_current_season(team)` | 写入前校验队伍是否属于当前赛事 |

已按赛季限定：首页统计与最新队伍、`/api/teams`、赛事大厅统计与动态、`/admin/matches`、`/admin/schedule`（含原生 SQL）、`/admin/draw`（含原生 SQL）、`/admin/schedule/api/matches`、手动排赛的选手查找、选手邀请列表与个人中心邀请。

已拒绝跨赛季写入：接受邀请、申请加入队伍（旧赛季队伍一律拒绝并给出提示）。

积分重算默认仅当前赛季，且只累计已确认结算的整场成绩，使用保存的难度倍率；函数不自行提交。往届仅超管专项纠错可按该届快照重建，完整写入与审计统一提交。

整场与日程分段共用一份成绩。管理员确认结算后才计入成绩，弃权即时记胜负并等待资料及结算，审核驳回保留已经记录的积分和胜负。轮空不产生比赛或战绩。队员比赛积分加有效人工调整后，再计算队伍倍率。并列占位跳号，晋级线同分全部晋级。按 [积分联验](P1-5与P1-6联验.md) 和 [阶段准入矩阵](P1-4实施与验证.md#阶段准入) 操作。

### 6.3 往届赛事归档页

入口：导航栏「往届赛事」→ `/history`（公开只读）。

| 路由 | 内容 |
|---|---|
| `GET /history` | 历届赛事卡片：届数、起止日期、队伍数/场次/已完成数、冠军队伍及积分 |
| `GET /history/<id>` | 该届详情：冠亚季军领奖台、队伍积分榜、队员积分榜、全部比赛结果（含比分与胜者） |
| `GET /history/<当前赛季 id>` | 302 跳转到赛事大厅（当前赛季不在此页重复展示） |

规则：

- 首页、赛事大厅、排行榜只展示**当前赛季**数据，往届数据一律进入 `/history`。
- 往届数据只读：`/history` 不提供任何写入操作。
- 若某届只有比赛没有积分，页面会显示「暂无积分数据」而不是报错。

「我的比赛」和选手资料默认显示本届，选「累计」可看有明确届次的整场，往届旁标明届次。选手详情 API 用 `season=current` 或 `season=all` 选择范围，按 ID 和昵称使用同一口径。往届纠错由超管在历史专项入口说明原因并审计，资料缺失先按 [历史核对流程](P0实施与验证.md) 处理。

### 6.4 排赛与抽签工具

| 入口 | 用法 |
|---|---|
| 后台「执行匹配」及「日程管理」 | 服务端保存正式比赛和日程。自动匹配按启用赛道分组，按查询顺序配对不同队伍的选手。时间意愿或位置可由组织者人工参考。 |
| 后台「分组抽取器」 | 从日程接口读取已创建的正式比赛，在浏览器随机重分组供现场展示。生成的分组停留在页面。 |
| 独立 `抽取/` 工具 | 可选的静态前端，独立运行。使用前更新 `public/data/players.json`、`src/utils/filter.ts` 的赛道映射和 `public/image/` 的头像。使用适合现场公开的字段。 |

正式赛程的调整请在「日程管理」执行。独立工具由组织者手动维护数据，主应用的复用验收以其服务端和后台为准。

## 6.5 开启新赛季会发生什么

点「开启新赛季」后：

| 对象 | 处理 |
|---|---|
| 旧 `Tournament` | `is_active=False`、`status='finished'`（数据全部保留，可按 id 访问详情） |
| 新 `Tournament` | 新建，状态 `registration`，`bonus_score` 继承上一届 |
| **用户** | **全部保留**（用户名、密码、角色、新手引导完成状态都不变） |
| `User.status` | 非管理员统一归零（参赛进度：入队/选赛道/报时间等需重新走） |
| 队伍 / 队员 | 旧队伍保留在旧赛季；`User.team` 与 `get_team_membership()` 按当前赛季过滤，所以需要**重新建队、重新邀请** |
| 上届 pending 邀请 / 加入申请 | 自动删除（避免误操作到已归档队伍） |
| `TimePreference` | 清空 |
| `Invitation` / `JoinRequest` 历史记录 | 已处理的保留 |
| `Setting` | 晋级名额按选择继承或归零，队伍全局设置保留。新赛季的报名开关初始关闭。 |
| 展示位置 | 上届的积分、比赛结果不再出现在首页/赛事大厅，统一在「往届赛事」（`/history`）查看 |

> 结论：**保留全部用户 + 重建队伍**是官方支持路径；同一队长、同一队名可以在新赛季重复使用（唯一约束按赛事隔离）。

换季向导链接到规则管理、赛道管理和报名控制。新赛季沿用全局编辑源，归档保留上届快照。换季后先处理仪表盘待办，手动开放报名须有至少一条启用赛道。继承的日期用于提醒。

### 6.6 赛事发布包

超级管理员从「数据工具 → 赛事发布包」进入。数据库结构版本 5 保存每届的草稿和已发布版本。升级前用原代码和 `APP_VERSION` 生成完整备份并保留，在执行 `prepare` 前停止旧服务。

1. 选择「从当前配置生成草稿」。清单记录赛道难度、规则及发布状态、队制、倍率、晋级、计划时间、术语、排赛时段、品牌色和轮播素材的相对路径及 SHA-256。处理提示中的规则正文、启用赛道、日期、素材或兼容性问题后重新生成草稿。
2. 选择「发布当前配置」。每次发布分配本届的新版本号，保存发布人、时间、规则快照与应用/schema 版本，并重新计算清单校验值。配置变更后重新生成草稿再发布。「已发布版本」可下载 JSON 和 Markdown，往届详情显示该届最新发布版及校验值。
3. 新届处于报名阶段、开关关闭且尚无队伍或比赛时，可把既有版本「复制到草稿」，也可上传 JSON。跨实例时，按清单配置目标实例的赛事时区、术语、队伍位置、排赛默认值、难度默认值及品牌色。用清单中的相对路径把同一素材放到目标 `IMAGE_DIR` 或 `UPLOAD_ROOT`。素材文件随原有备份或通过运维渠道迁移。使用目录回退轮播时，目标目录的可用轮播文件也须与清单一致。
4. 校验后点击「备份并应用到本届」。系统保留目标届名和届次、更新规则与赛道配置并替换本届轮播，保留未列入包的赛道标识并停用。来源版本记录在本届及后续发布清单。应用完成后由管理员核对本届配置并手动开放报名。

发布包的用途是复用赛事配置。账号、队伍、成绩、操作日志、部署密钥及素材文件内容由独立的备份流程管理。应用配置前会保存可校验的完整备份批次及审计记录。在新届尚无业务数据时，可复制旧版配置再应用。需要恢复完整运行状态时，使用匹配的应用版本在空库与独立目录执行 [恢复演练](P0实施与验证.md#备份与恢复)，核对旧版本、业务数据和附件。
