## 实现范围

| 事项 | 实现 |
|---|---|
| P0-1 按赛季重算 | 默认唯一活跃赛季，无 active 无副作用，多 active 明确拒绝；只累计正式整场已确认结算成绩。发现关联本届队伍的缺失/冲突归属时先拒绝，保留原分数。重算不自行 commit，调用者统一提交审计。 |
| P0-2 历史倍率与规则 | 原始成绩首次保存前固化难度区间、步长、取整规则和 Numeric(8,4) 倍率；比赛绑定已发布上下文版本。改 raw 保持历史规则；改难度按保存的规则换算。后台详情显示原始分、倍率、换算积分和结算状态。 |
| P0-3 迁移与并发 | 显式 `prepare`、schema_version=1、目标引擎识别、SQLite/MySQL 补列及唯一约束/外键校验。升级前一致备份；失败退出，不记录成功版本。SQLite DDL 事务回滚；MySQL DDL 的隐式提交不能假装回滚，失败后必须用已验证批次恢复到匹配版本的隔离目标。 |
| P0-4 原子换季 | 服务端签发令牌、持久化处理结果、校验 expected_current_season_id、进程间维护锁、条件更新和届数/转换记录唯一约束。相同令牌重放返回同一结果；不同令牌旧页面至多一次成功。数据库/素材备份在前，业务、清理、配置、审计、幂等结果同一事务。 |
| P0-5 归档保护 | 普通比赛、队伍、成员、邀请/申请、排赛、轮播等写入口校验真实归属；孤儿拒绝放行。保护只有往届成员关系、没有比赛的账号。ScoreLog 和上下文版本不可改删，MySQL 审计前后值用 LONGTEXT。超管通过独立页纠错，必填原因，保存完整前后值及该届榜单变化，审计失败回滚。 |
| P0-6 上下文及赛道 | 保存不可改写的 SeasonContextVersion；归档展示冻结的规则、赛道名称和赛制，昵称/头像继续跟随账号。引用过的赛道 key 不可改/删/复用，可停用。默认赛道仅在显式空库初始化播种。 |

同时完成 P0 所需前置：应用导入/工厂无建库副作用、整场与日程段区分、双方唯一成绩、明确确认结算、弃权即时胜负与延后积分、0 分保存、最小可持久化人工调整/撤销，以及数据库和备份持久化配置。

P1–P3 的其他事项没有据此全部标为完成。计分器 P4/P5 和表演赛专项继续暂缓。已有表演赛不在本轮重新决定计分/胜负政策；重算保留其原来已结束记录中实际关联成员的贡献语义，有贡献但缺失历史快照时仍须人工核对。

## 关键文件

- `app.py`：模型、工厂、原有页面与成绩入口。
- `season_safety.py`：归属守卫、上下文版本、换季、超管纠错、审计保护。
- `scoring.py`：按季、按整场与结算状态重建。
- `migrations.py`：版本 1 迁移、旧结构识别、索引/外键与成功版本校验。
- `backup.py`：维护锁、数据库/素材批次、哈希清单、恢复与保留最近 5 个完整批次。
- `management.py`：prepare/data-report/reconcile/backup/restore-rehearsal。
- `wsgi.py`：加载已准备的应用；worker 不执行迁移或播种。
- `tests/`：合成旧库结构、接口、故障、恢复、线程和独立进程回归。

## 原生运行（Python 3.12，Linux）

```bash
python -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt

# 原生入口不会自动读取 .env，请先设置/导出实际环境变量。
export FLASK_ENV=production
export SECRET_KEY='请设置为本实例的随机值'
export ADMIN_PASSWORD='请设置管理员初始口令'
# 如需超管：同时设置 SUPER_ADMIN_USERNAME / SUPER_ADMIN_PASSWORD。
# DATABASE_URL 未设置时默认使用 .db/lskb.db。

python -m flask --app 'app:create_app()' prepare
python run.py
```

已有库的 prepare 会先备份并执行显式迁移。正常重启和导入不再自动建表、升级或补回默认赛道。
prepare 不会替旧数据猜测历史规则，也不会把无 active 的有数据实例自动变成新赛事。

生产多 worker：安装 Gunicorn 后运行 `gunicorn --workers 4 wsgi:app`。
不要继续使用旧的 `gunicorn app:app`。

## Docker

MySQL：`docker compose up --build`。
SQLite：`docker compose -f docker-compose.sqlite.yml up --build`。

镜像启动顺序是单进程 prepare 成功后启动 Gunicorn。SQLite 目录（含 WAL/SHM）、MySQL 数据、上传、维护锁和 backups 均使用持久卷；独立实例用不同 Compose 项目名和端口。MySQL 库名、用户、密码分开传入 URL.create，避免特殊字符拼接错误。

本环境使用证书代理时，构建命令为：

```bash
docker build --secret id=pip_ca,src=/etc/ssl/certs/ca-certificates.crt -t lskb-p0:local .
```

CA 仅作为构建 secret 使用，不写入镜像，也不关闭 TLS 校验。普通网络不需要传该 secret。

## 换季和纠错

1. 后台赛事设置页生成本次令牌并展示未结算整场。
2. 普通切换遇未结算会拒绝；强制切换须勾选并填写原因，日志保存冻结的场次清单。不会把它们自动改成完成、取消或 0 分。
3. 本次切换前必须完成数据库与素材的一致备份，失败不切换。上届用户保留、队伍保留、进度归零；待处理邀请/申请清理，已处理记录保留。
4. 往届正常页面只读。超管可在 `/admin/history-corrections/<赛季ID>` 修改历史 raw/难度；使用该场原规则，必填原因。强制归档的未结算整场，如历史规则已保存，可补齐资料后通过该专项入口显式确认结算。
5. 当前队伍页的人工总分调整转换成独立 delta，有原因和撤销记录，重算保留；先加队员调整，再乘该届 bonus。

## 旧数据人工核对

```bash
python -m flask --app 'app:create_app()' data-report > review.json
python -m flask --app 'app:create_app()' reconcile --plan approved-plan.json --operator 超管用户名
```

data-report 只读：列出多个 active、空队伍归属、比赛双方归属冲突、缺规则/结算基准、独立计分分段、缺上下文、成员/队伍存储总分。提供双方队伍与日期区间候选及依据，不自动写库。

reconcile 仅接受 `confirmed: true`、必填 reason、当前报告 digest 和存在的超管操作者。先备份，再按人工确认方案写入与审计；任何异常回滚业务。已有规则不能通过该入口覆盖，应走专项纠错。报告改变时方案失效。

方案示例（示意 ID/分值，必须根据实际报告和原始依据填写；不能照抄）：

```json
{
  "confirmed": true,
  "reason": "核对原始赛事规则、截图与成员归属",
  "report_digest": "当前review.json的digest",
  "teams": [{"id": 8, "tournament_id": 2}],
  "seasons": [{
    "id": 2,
    "context": {
      "version": 1, "name": "原赛事名", "season_number": 2,
      "bonus_score": 500, "team_size": 4,
      "positions": ["cold", "normal1", "normal2", "pit"],
      "labels": {"track": "肉鸽", "field1": "分队", "field2": "开局干员"},
      "tracks": {}, "rules": [], "score_contract": "人工核对的当届口径"
    }
  }],
  "matches": [{
    "id": 12, "tournament_id": 2,
    "rule": {"version": 1, "track_key": "water", "minimum": 12, "maximum": 18,
```

上例 tracks/rules 省略了实际条目以展示结构；真实历史内容必须由人工核对提供。新旧累计有差异时需逐成员/逐队明确确认 before/after，不会把所有差额自动变成人工调整。
`segments` 项可明确指定 `id` 与 `formal_match_id`，把旧分段归并到已人工确认的整场；原始 raw/结果/难度/截图文本保存到 legacy_payload 和 ScoreLog，不删除原记录。

## 备份与恢复

```bash
python -m flask --app 'app:create_app()' backup
python -m flask --app 'app:create_app()' restore-rehearsal \
  --batch backups/具体批次 \
  --destination-url sqlite:////绝对路径/隔离目录/recovered.db \
  --media-destination /绝对路径/隔离目录/media
```

每批包含 database.db 或 database.sql、media.tar.gz、manifest.json。清单记录 UTC 时间、schema、源代码版本、逻辑目录映射、哈希和关键表行数，不含口令。
恢复目标必须是独立空库和空目录，禁止源库；验证文件哈希、解包路径和表行数。素材位于目标的 uploads/ 与 image/；运行恢复应用时设置相应 UPLOAD_ROOT、IMAGE_DIR 和新的 STATE_DIR/BACKUP_DIR，再验证页面/附件。

MySQL 需在执行进程 PATH 中安装 mysqldump/mysql 兼容客户端和一致性导出权限；只显示命令不算成功。Docker 已安装客户端。

升级前的 schema=0 备份匹配旧代码版本，默认 LEGACY_APP_VERSION=8238f20；其他来源须显式设置正确的旧版本。恢复旧批次时传 `--code-version 对应旧版本`，先按该版本验证，不能声称它可直接用 P0 schema 启动。MySQL DDL 失败后保留原批次，不执行盲目自动降级。

备份还会检查数据库引用的头像、队伍照、成绩截图和可识别轮播本地路径是否存在，引用缺失不会登记完整成功。

运行期间所有应用写请求和 CLI 准备/备份/核对共用维护锁；一个实例的 worker 必须共享 STATE_DIR。外部脚本或人工替换素材也必须在同一维护窗口停写，不能绕过锁。多个独立实例不能指向同一业务库/素材目录。
